# Серверное оформление заказа в МойСклад

Этот порядок относится к серверному созданию заказа покупателя. Он не включает
автоматический резерв, оплату, закупку у поставщика или отгрузку. Наличие файлов,
миграции и зелёного CI не подтверждает работу реальной интеграции.

Очередь пополняют прямое оформление всей корзины по известным условиям и новое
принятие обычного предложения, если интеграция включена для этого партнёра.
Принятые раньше заявки не ставятся в очередь автоматически. Перед ручным созданием
документа менеджер проверяет очередь и уже возвращённый UUID.

Архитектура: [ADR-0015](../adr/0015-shop-order-automation.md). Согласование
неизвестных условий: [закупки](procurement.md). Персональный магазин МойСклад
сохраняется постоянным вариантом заказа, включая период работающей автоматизации.

## До включения

1. Назначить ответственного за очередь отправки, индивидуальные условия, подтверждение
   наличия и сверку с документами МойСклад. Уточнить, кто обрабатывает задержки и отказы.
2. Проверить целевой проект, ветку и SHA. Сделать закрытую [копию](backup-restore.md)
   и пробное восстановление. Новые приватные таблицы заказов, их состав и ключи
   повторов должны попасть в копию. Сохранить UUID уже созданных внешних документов.
3. Для каждого включаемого партнёра подтвердить контрагента UUID, персональный тип
   цены, валюту и применяемые скидки. Нельзя подставлять общий прайс или выбирать
   первую из нескольких привязок без проверенного правила.
4. Подтвердить организацию, склад, разрешённый ассортимент, базовые единицы и правила
   НДС. Не менять исходные цены, единицы или настройки персональных магазинов ради
   совместимости. Неподдержанное сочетание условий остаётся ручным согласованием.
5. Выдать отдельному серверному пользователю МойСклад минимальные необходимые права
   чтения и создания заказа покупателя. Подключение сервиса в ChatGPT не выдаёт
   приложению токен. Доступом к редактированию цен и складских документов этот
   исполнитель автоматически не наделяется.

## Проверка кода перед размещением

Из корня репозитория:

```sh
npm ci
npm run gen:contract
npm run typecheck
npm test
npm run build
git diff --check
```

Проверить diff сгенерированного контракта, серверную авторизацию и тесты очереди.
Контрольные сценарии:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Аноним, сотрудник без доступа, чужой партнёр, отозванная сессия | Заказ и чужая цена недоступны |
| Подмена цены, валюты, контрагента или количества в браузере | Сервер сверяет свои условия и отклоняет несовпадение |
| Два нажатия и повтор после перезагрузки | Один заказ приложения и исходный ключ внешней отправки |
| Два исполнителя одновременно | Одно задание не исполняется параллельно без согласованной блокировки |
| МойСклад создал документ, ответ потерян | Сверка исходного идентификатора до нового POST |
| Режим сверки, внешний документ не найден | Новый POST не выполняется; результат остаётся отдельным состоянием |
| Принято 8 сейчас + 12 позже по разным ценам | Обе согласованные цены и количества сохраняются в одном заказе |
| Единица товара/родителя модификации изменилась после согласия | До POST срабатывает отказ; количество не трактуется в новой единице |
| Нет токена, конфигурации, цены или привязки | Автоматический путь недоступен, общий прайс не подставляется |
| Остаток изменился или устарел | Нет обещания резерва; требуется проверка/новое согласование |
| Созданный заказ восстановлен из копии | UUID и ключ отправки сохраняются, повтор не создаёт второй документ |
| Ошибка интеграции | Выручка, смены, вход и `lead_submit` продолжают работать |

Проверять не только отдельные функции, но и совместимость SQL/HTTP: версию
конфигурации в импорте, имена аргументов RPC, ответ без тела у `void`-команд,
состояния получения задания и подтверждения результата. Mock не должен
подменять эти ответы удобной, но отсутствующей в настоящем API формой.

Телефон и компьютер проверить на ширинах из `AGENTS.md`, с 200% текста,
длинными товарами, пустой корзиной, ошибкой сервера и неизвестным результатом.
Проверить обновление уже открытой PWA с незавершённым вводом.

## Размещение сервера

Миграции применяются сначала к изолированной цели, затем к явно проверенной рабочей
базе по [общему порядку](deploy.md). `npm run db:apply` использует защищённый
`DATABASE_URL`. Запускать без seed/reset/restore и не переписывать старые миграции.
Автоматизация остаётся выключенной до готовности конфигурации и исполнителя.

Конфигурацию меняет владелец БД в закрытой схеме, проверив реальные исходные
документы; общего пользовательского редактора этих настроек пока нет:

| Таблица | Что проверить перед `enabled=true` |
| --- | --- |
| `app_private.procurement_shop_settings` | `organization_id`, `store_id`, явные `folder_ids`, `verified_by`, `verification_note` |
| `app_private.procurement_shop_partner` | `partner_id` и принадлежащий ему `counterparty_id`, `price_type_id`, `currency`/`currency_id`, явные `allowed_folder_ids`/`allowed_product_ids`, отсутствие скидок, НДС, автор/дата/основание проверки |

Ценовая политика этой версии — `price_type_only_verified`: подтверждённый тип
цены без активных скидок/бонусных программ, валюта с двумя десятичными знаками,
прямой курс и кратность один. НДС либо отключён, либо уже включён в цену.
Автоматический пересчёт дополнительного НДС, скидок или валют не выполняется.
МойСклад остаётся источником исходных настроек; таблицы приложения их не меняют.

Сначала сохранить проверенные настройки выключенными. После настройки секретов
и тестов включить глобальную конфигурацию и только проверенного пилотного партнёра,
затем выполнить один `sync`. Оформление останется недоступным до успешного свежего
импорта, корректной привязки и рабочего heartbeat. Только после сверки результата
подключать `dispatch`/расписание. Старые задания, восстановленные из копии, до этого
разобрать отдельно. Изменение конфигурации повышает её версию; не исправлять версию
вручную ради выполнения прежнего задания.

Серверная функция: `supabase/functions/shop-worker/index.ts`.
Секреты размещаются в защищённом окружении Edge Function:

| Переменная | Назначение |
| --- | --- |
| `MOYSKLAD_TOKEN` | Выделенный серверный токен МойСклад для согласованных действий |
| `SUPABASE_URL` | Адрес целевого проекта; предоставляется средой Supabase |
| `SUPABASE_SECRET_KEYS` | Секретные серверные ключи среды; предпочтительно отдельный ключ `shop_worker` |
| `SUPABASE_SERVICE_ROLE_KEY` | Legacy-альтернатива серверному ключу, если используется этим проектом |

Ни одна из этих секретных переменных не имеет префикса `VITE_`. Не помещать их
значения в git, историю команд, браузер, логи или скриншоты. Файл для загрузки
секретов создаётся вне репозитория с ограничением доступа.

Перед командами проверить `npx supabase --version`, `npx supabase secrets set --help`
и `npx supabase functions deploy --help`: интерфейс CLI меняется. Проверенный в
этой работе синтаксис выбирает явную цель через `--remote`:

```sh
npx supabase secrets set --remote="$SHOP_PROJECT_REF" --env-file "$SHOP_SECRET_FILE"
npx supabase functions deploy shop-worker --remote="$SHOP_PROJECT_REF" --no-verify-jwt --use-api
```

`SHOP_PROJECT_REF` — проверенный идентификатор проекта; `SHOP_SECRET_FILE` — путь
к закрытому файлу с `MOYSKLAD_TOKEN`. Ключи `SUPABASE_*` не загружать повторно,
если их предоставляет среда. Флаг `--no-verify-jwt` допустим только вместе с
собственной проверкой точного серверного ключа в обработчике: новый secret key
не является пользовательским JWT. Публичный вызов и пользовательский access token
должны получать отказ. Серверная функция не вызывается непосредственно браузером.
Для заранее проверенного неинтерактивного запуска CLI v3 требует `--yes`; без него
ошибка подтверждения не означает, что размещение состоялось.

После размещения сначала проверить отказ без ключа и безопасный ответ при
выключенной конфигурации/отсутствующем токене. Ошибка должна возникать до получения
задания и до HTTP-записи в МойСклад. Непроверенный endpoint не включать расписанием.

Допустимое тело POST: `{"action":"sync"}`, `{"action":"dispatch"}` или
`{"action":"run"}`. `dispatch` получает не более одного задания за вызов;
`run` сначала обрабатывает очередь, затем обновляет снимок, чтобы сбой нового
импорта не препятствовал сверке прежней отправки. Для администратора допустим точный
серверный ключ через `apikey` либо legacy `Authorization: Bearer`; расписание
использует отдельный ограниченный `x-shop-worker-key`, описанный ниже. Тело не
позволяет выбрать партнёра, внешний URL или произвольный состав документа.

Контроль очереди владельцем БД без вывода содержимого заказов:

```sql
select status, count(*) as orders, min(created_at) as oldest
from app_private.procurement_order_outbox group by status order by status;
select enabled, worker_status, last_heartbeat_at, last_success_at, error_code
from app_private.procurement_shop_settings where singleton;
```

`queued`/`retry` ожидают отправки, `processing` — действующую аренду задания,
`reconciling` — сверку неизвестного результата, `created` — подтверждённый UUID,
`blocked` — вмешательство ответственного. `created` не означает резерв или оплату.
Число попыток ограничено; после исчерпания нужен разбор, а не новый ключ операции.
При смене конфигурации или отзыве доступа неизвестная прежняя запись может только
сверяться; это не разрешение на новый POST.

Текущий минутный `run` обслуживает не более одного задания за запуск. Срок снимка
прямой покупки — пять минут: очередь из нескольких одновременных заказов способна
дожидаться проверки дольше этого срока. Перед массовым включением измерить очередь
на ожидаемом потоке, отдельно настроить более частый `dispatch` и проверить квоты
API/аренды; ускорение отправки не требует повторять полную выгрузку каталога.
Текущий график не объявляется рассчитанным на произвольный рост сети.

## Расписание в Supabase

Миграция `20261108162500_shop_scheduler.sql` только устанавливает закрытую функцию
настройки. Она сама не запускает задание и не включает оформление. Для размещённого
`shop-worker` владелец БД вызывает:

```sql
select app_private.shop_scheduler_install(
  'https://<проверенный-ref-проекта>.supabase.co/functions/v1/shop-worker'
);
```

Вместо шаблона нужен точный URL своего проекта; регулярное выражение в функции
проверяет форму URL, а не соответствие выбранной БД. Доступ к установке закрыт для
`anon`, `authenticated` и `service_role`. Требуются Vault, `pg_cron` и `pg_net`;
в локальном окружении без них функцию не запускать.

Установка сохраняет отдельный случайный секрет `bron_shop_worker_key` в Vault,
в прикладную таблицу помещает только его хеш. Задание `bron-shop-worker` раз в
минуту вызывает `action=run` с заголовком `x-shop-worker-key`. В тексте cron-задания
содержится чтение Vault, а не значение ключа. Установка возвращает только служебные
метаданные. Не выводить `vault.decrypted_secrets`, командные HTTP-заголовки или
секрет в журнал диагностики.

Проверка владельцем БД без вывода секретов:

```sql
select jobid, jobname, schedule, active
from cron.job where jobname = 'bron-shop-worker';
select j.jobname, r.status, r.start_time, r.end_time
from cron.job_run_details r join cron.job j on j.jobid = r.jobid
where j.jobname = 'bron-shop-worker'
order by r.start_time desc limit 10;
```

Успешная отправка `net.http_post` из cron ещё не доказывает успешный ответ функции
или создание заказа. Проверить ответ HTTP, журнал функции и состояние очереди.
Без токена/включённой конфигурации штатный ответ об отключённой автоматизации
ожидаем; он не должен создавать внешние документы.

Остановка только этого задания:

```sql
select cron.unschedule(jobid)
from cron.job where jobname = 'bron-shop-worker';
```

Прикладная JSON-копия не переносит Vault, Edge-секреты и cron автоматически.
После восстановления на другой проект установить/сверить функцию, секреты и
расписание отдельно. До сверки исходных заказов исполнитель должен быть выключен.
Повтор установки в прежнем проекте использует существующий Vault-секрет;
это не процедура ротации скомпрометированного ключа.

## Приёмка

### Проверено 08.11.2026 перед публикацией клиента

- 198 автоматических тестов, TypeScript, генерация контракта и production build прошли.
- Браузер: 72 сочетания размера/роли/состояния магазина и 48 экранов остальных
  разделов; переполнение документа и слишком мелкие поля не обнаружены после
  загрузки шрифтов. Дополнительно проверены корзина 20/8, оформление 8 из наличия
  и форма условий менеджера на 320 px с текстом 200%. Это не проверка физического iPhone.
- Закрытая копия создана и восстановлена в изолированной базе. После двух новых
  миграций контрольные суммы всех 39 существующих бизнес-таблиц совпали.
- `shop-worker` размещён, вызов без ключа возвращает HTTP 401. Закрытое расписание
  вызывает функцию; её ответ `missing-token`, состояние `disabled`, заказов в очереди 0.
  Существующее задание `bron-jobs` не изменено.
- Глобальное оформление выключено, персональные конфигурации не активированы.
  Серверного токена МойСклад нет; текущий наследуемый НДС каталога и персональный
  ассортимент требуют подтверждения. Успешная реальная отправка заказа не заявляется.

Зелёные проверки и размещение выключенного исполнителя не заменяют следующий
пилот с реальной согласованной закупкой.

В изолированной интеграционной среде проверить полный путь: действующая сессия
партнёра → персональные условия → согласие → очередь → один заказ МойСклад →
подтверждённый UUID в кабинете. Сверить контрагента, организацию, склад, количество,
единицу, цену, валюту, скидку и НДС. В позициях не должно появляться автоматического
резерва. Затем повторить тот же запрос и проверить число внешних документов.

Реальный заказ для рабочей проверки должен быть реальной согласованной закупкой.
SQL `ROLLBACK` не отменяет HTTP-запись МойСклад: не использовать его как разрешение
создавать фиктивные внешние заказы. Проверку сетевого обрыва после POST сначала
проводить в изолированной среде.

После включения записать SHA клиента и функции, имя миграции, время снимка,
подтверждённую область партнёров, результат проверки и отдельные непроверенные
сценарии. Расписание и мониторинг считать включёнными только после наблюдения
успешного запуска, отказа и восстановления. CI/Pages не развёртывают Edge Function
автоматически, если workflow явно этого не делает.

## Сбой и откат

1. Выключить автоматизацию и остановить расписание/исполнителя. Остановить новые
   попытки отправки; уже выполняющийся внешний запрос может завершиться.
2. Сохранить заказы, очередь, исходные идентификаторы и ошибки. Не удалять задания
   и не создавать новый ключ из-за таймаута. Сверить неопределённые отправки с
   МойСклад по исходному идентификатору, контрагенту и позициям.
3. Вернуть совместимую предыдущую клиентскую сборку/функцию при необходимости.
   Новые таблицы оставить закрытыми и сохранить историю. Откат клиента не отменяет
   уже созданные документы МойСклад.
4. Для продолжения через персональный магазин сначала выяснить, существует ли
   прежний заказ. При наличии — работать с ним; новую покупку не дублировать.
5. Исправить причину, проверить повтор и включать обработку оставшихся заданий
   теми же идентификаторами. Отмену/изменение внешнего документа менеджер выполняет
   отдельно по действующему процессу МойСклад.

Сбой интеграции не требует отката базы целиком, удаления пользователей или
остановки заявок лендинга. Восстановление копии поверх рабочей базы может потерять
новые заказы; это отдельная аварийная процедура, а не обычный откат функции.
