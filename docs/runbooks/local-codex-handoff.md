## 3. Подключение без нового сервера

12.11 владелец выполнил на Mac `nc`: **оба TCP-соединения успешны** —
`aws-1-us-west-2.pooler.supabase.com:5432` и `152.228.115.115:22`.
Это ещё не SSH-аутентификация, TLS или доступ к БД. Из прежней облачной среды
SSH недоступен; из VPS source:5432 получает таймаут до TLS/пароля.
Обращение AdminVPS **№482050 отправлено** с разрешения владельца: только исходящее
исключение на срок переноса, без платных услуг. Не жди исключительно ответа;
не дублируй обращения. Старое №521292 касалось активации/hostname, ответа не было.

Проверь SSH host key через доверенную VNC-консоль провайдера:

```sh
ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
```

Fingerprint ED25519 по сетевой проверке и сверке доверенной VNC локальным Codex
12.11, [отчёт](local-access-result-20261112.md):
`SHA256:8KA0F5NRZo8hIn84yT/pSclefFxk8zRg9JzuPuilYh0`.
Прежняя ручная расшифровка скриншота была ошибочной; её не использовать.
Сверь с ключом SSH перед первым входом; при несовпадении остановись и перепроверь
через панель провайдера.
Не использовать `StrictHostKeyChecking=no`. Root SSH-аутентификация пока не
проверена: владелец при необходимости вводит пароль лично в скрытом Terminal.
Настрой постоянный ключ владельца, проверь отдельный вход; сохрани аварийный VNC
и не отключай работающий доступ раньше проверки замены.

Если прямой исходящий доступ VPS ещё закрыт, используй стандартный временный канал:

```sh
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -R 127.0.0.1:15432:aws-1-us-west-2.pooler.supabase.com:5432 \
  root@152.228.115.115
```

Проверь на VPS listener **только `127.0.0.1:15432`**, настройки forwarding и
отсутствие публичного порта; Mac держать включённым и подключённым. При явном
запрете провайдера остановись, не обходи его другими маршрутами. pg_dump работает
на VPS; PostgreSQL TLS проверяет канонический hostname end-to-end. Mac передаёт
зашифрованный трафик, выгрузки на нём не создавать.

CA источника: `/opt/bron/source-ca.crt`, bundle `/opt/bron/source-ca-bundle.pem`.
Официальный сертификат:
<https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt>,
SHA-256 `700723581420dd1ac98fd7e9ac529f0ef210eadcaf87fc868a3ad7d114c2f3b7`.
Не ослаблять TLS. Libpq: canonical `host`, `hostaddr=127.0.0.1`, `port=15432`,
`dbname=postgres`, `user=postgres.vkkqffvmztpzgygzfxhq`, `sslmode=verify-full`.
pgpass сопоставляется с **canonical host и портом15432**, не с IP/5432.

`BRON_SOURCE_TUNNEL_PORT=15432` либо `--tunnel`; текущий SHA-256
`05b381f28f69377f87a980b7444190fa00047544d81b6b0f9d65ad1d8a68817e`.

`6b51705679976b6f2c4f1b0412ec9bd3973889e3232e726286553bc0f23b7f23`;

## 4. Полная копия и репетиция

Действуй по актуальной [официальной процедуре](https://supabase.com/docs/guides/self-hosting/restore-from-platform).
**Особенность CLI3.1:** обычный `db dump` не передаёт `hostaddr` своему клиенту.
Для канала проверь адаптер официальных `--dry-run` сценариев и нативный PG17.11
на VPS: сохранить vendor-фильтры roles/schema/data, убрать только dummy-export
`PGPASSWORD`, явно передать защищённый pgpass, canonical host/hostaddr/port и
TLS/CA. Не печатай реальные URL/пароли. Это ещё не реализованный экспорт.
Сохрани `default_transaction_read_only=on`, остановку при первой ошибке и запись
в `.part`: неполный дамп не переименовывать в готовую копию.
`migration:check`/`migration:leads` также требуют проверенного транспорта:
общий `database-config.mjs` запрещает URL `hostaddr`. При необходимости добавь
узкий проверяемый адаптер с canonical TLS; не ослабляй общий запрет и не включай
plaintext до Supabase через `BRON_DB_ALLOW_LOCAL_PLAIN`.
Согласованность schema/data обеспечь общим экспортированным snapshot либо
проверенным окном без изменений; отдельные запуски CLI сами этого не гарантируют.

Сохрани Auth/identities/пароли, прикладные схемы, grants/RLS/RPC, Storage policies,
все объекты с размерами/SHA-256, конфигурацию Auth/JWT/SMTP, функции и расписания.
**Vault исключён стандартными фильтрами**: отдельно сохранить секреты/ключи и
проверить расшифровку на цели. Источник: активный cron `bron-jobs` каждые5 минут,
выключенный `bron-shop-worker`, Edge Function `shop-worker`; выключенное не включать.
На репетиционной цели держи восстановленные cron/воркеры выключенными до проверки
адресов и секретов, чтобы они не вызвали рабочие интеграции.

Секреты/PII/копии — только закрыто в РФ, без чата, скриншотов, argv, git, Actions,
shell tracing и логов. Зашифруй независимую копию в существующем S3; восстанови
**из S3** на изолированной цели, прежде чем менять источник/переключать клиентов.
Проверь объём1GB; при нехватке предъяви конкретную смету, не покупай автоматически
и не урезай молча хранение. JSON не использовать как замену SQL/Auth.

Создай новые секреты в закрытом `.env`; публичные URL и Auth `/auth/v1` — по
deploy README. Закрой регистрацию, Studio/БД/pooler извне, проверь Docker firewall.
После восстановления **сначала** `npm run migration:check`: значения/UUID,
хеши, права, расширения, последовательности и финансы по отдельным валютам,
не одни количества. Затем изолированные проверки входов и записи. На цели
перед открытием отозвать перенесённые sessions/refresh tokens, сохранив users и
identities; новый JWT secret сам по себе этого не делает. Источник не отзывать.

## 5. Завершение и единственная рабочая запись

1. Проверь директора, франчайзи/сотрудника, чужую область, анонима, отозванную
   сессию, смены, выручку/роялти, документы, повтор/конфликт/потерю сети на копии.
   Рабочую БД не засоряй фиктивными деньгами/лидами.
   После пробных записей выполни чистое финальное восстановление либо проверенный
   перенос изменений всех затронутых таблиц; `migration:leads` переносит лишь заявки.
2. Собери оба существующих сайта; сохрани контракт лендинга
   `POST /rest/v1/rpc/lead_submit`, `{"p_lead":{...}}` → `{"ok":true}`;
   `anon` отправляет, но не читает. Подготовь поздние UUID по runbook.
3. Настрой HTTPS/Caddy и явные DNS `@`/`app`/`api`; не добавляй непроверенный
   AAAA/wildcard. DNS сначала подготовь; рабочее переключение — после финальной
   сверки в п.4. До открытия оставь доступ к цели только администраторам.
4. В финальном окне: сохранить/отправить старые PWA-очереди, учесть открытые смены,
   ограничить старые команды, перенести дельту, повторить строгую сверку. После
   моментаT новые данные пишутся только в РФ. Поздние старые анкеты учесть;
   бессрочный зарубежный приём недопустим. DNS не меняет код открытой вкладки.
5. Старый Pages обновить на новый backend и сохранить возможность отправки
   origin-очереди с прежним UUID после входа. Не очищать IndexedDB и не делать
   безусловный redirect. Проверить старую установленную PWA, новую установку,
   реальные телефоны/Wi-Fi/мобильную сеть безVPN; iOS требует устройства владельца.
6. Настрой часовые зашифрованные копии, контроль возраста/ёмкости,24часовых,
   30дневных/12месячных точек; измерь восстановление. RPO≤1ч/RTO≤4ч — цели до
   измерения. Мониторинг каждые5мин: версия/Auth/ping/контракт без мусорной заявки,
   диск/память/контейнеры; проверь реальную доставку тревоги и восстановление сбоя.
7. Дай владельцу понятный порядок аварии/восстановления, ключи восстановления
   закрытым способом; назначение человека для обслуживания ещё не решено.
   Не обещай круглосуточное дежурство ИИ или оплаченный саппорт Supabase.

После изменений кода выполни typecheck, подходящие тесты, build/CI; сохрани git
как источник разработки и безопасный выпуск на VPS. Приватность репо менять
после проверки старых PWA/публичного Actions API. Исходник не отключать до сверки
новых записей, поздних заявок и очередей. После записи на цели откат требует
сверки/переноса дельты, одного возврата DNS недостаточно.

На время ограниченного локального этапа прежний агент не меняет VPS параллельно.
После безопасного отчёта локальный Codex останавливается, основная миграция
продолжается в прежнем чате. Веди краткий журнал SHA, команд без секретов,
проверок и результатов. Фиксируй отдельно «подготовлено/применено/опубликовано/
проверено». Не объявляй перенос завершённым при незакрытых критериях релиза.
