# Обновление рабочего приложения

Репозиторий: `bronservis51-bot/bron-franchise`. Публикация:
https://bronservis51-bot.github.io/bron-franchise/.
Текущая база настоящая; старый порядок первого демо-запуска к ней не относится.

## Перед публикацией

1. Проверить ветку, diff и целевую базу. Прочитать [AGENTS.md](../../AGENTS.md).
2. Для кода выполнить `npm ci`, `npm run typecheck`, нужные тесты и
   `npm run build`. При изменении RPC — `npm run gen:contract`, проверить diff
   сгенерированного контракта. Для документации достаточно ссылок и diff-check.
3. Перед изменениями БД сделать закрытую [копию](backup-restore.md) и проверить
   путь отката. Убедиться, что новые SQL испытаны в отдельном окружении.
4. Применить только новые миграции командой `npm run db:apply` к явно проверенной
   цели либо разрешённым инструментом миграций. Не редактировать SQL с уже
   сохранённым checksum. Не использовать `--seed`, `--after-users`, `seed:users`,
   `db:reset-demo` или restore с очисткой на рабочем источнике.
5. Проверить фактический результат SQL и права. Истёкшее подтверждение не означает
   применения. Учитывать совместимость старого клиента с новой схемой: на время
   перехода прежние вкладки продолжают выполнять запросы.

## Конфигурация и публикация

GitHub → Settings → Secrets and variables → Actions → **Variables** содержит
`VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Это публичные значения.
`service_role`, secret key, `DATABASE_URL`, токен МойСклад и пароли пользователей
в клиентские переменные не передаются. Все `VITE_*` считаются доступными браузеру.

Pages: Source = GitHub Actions. Workflow `pages` при изменении `main` проверяет
тесты, собирает `production` с base `/bron-franchise/` и публикует результат.
Workflow `ci` отдельно проверяет типы, тесты и сборку. Для обычной публикации не
нужны общий пароль и `VITE_DEMO_QUICK_PASSWORD`: этот механизм удалён.

После push/merge дождаться успешных CI **и** Pages для нужного SHA. Успех CI не
доказывает применения SQL к базе. `npm run deploy` — запасной способ публикации,
его конфигурацию и права проверять отдельно, не запускать автоматически.

## Проверка после публикации

- В новой вкладке открыть реальный URL и проверить личный вход. Если остался
  старый выбор ролей, закрыть старые вкладки кабинета и открыть заново: они могут
  удерживать прежний service worker. Не очищать пользовательскую очередь вслепую.
- Проверить затронутые сценарии менеджера, партнёра и сотрудника. Для изменения
  доступа также проверить чужую область и отозванную сессию; для денег — повтор
  и конфликт, не добавляя фиктивных финансовых данных в рабочий учёт.
- При изменениях приёмника/доступа убедиться, что `anon` сохраняет возможность
  `lead_submit`, но не чтение заявок. Не засорять рабочую очередь тестовыми лидами;
  запись SQL проверять с откатом, доставку реальных заявок — по их UUID.
- Записать SHA, статус миграций, фактические проверки и оставшиеся ограничения.

PWA предлагает обновление пользователю. Оно не должно активироваться при открытом
диалоге, незавершённой команде или очереди. Не возвращать принудительную перезагрузку.

## Разработка и отдельное демо

Для разработки использовать `npm run local:backend` и локальный URL, как описано
в [README](../../README.md). Если нужен новый облачный демо-проект с seed, сначала
убедиться, что он изолирован и пуст, и не путать его переменные с рабочими. Новый
рабочий проект заполняется восстановлением проверенной копии, а не демо-данными.

Перенос в РФ требует отдельной процедуры: [план](../rollout-plan.md) и
[технический чек-лист](../production-readiness.md).
