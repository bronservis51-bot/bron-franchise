# Заявки из старых анкет после переезда

Старые открытые страницы отправляют анкету в исходный Supabase. Обновление
лендинга и DNS не меняет код уже открытой вкладки. По
[ADR-0021](../adr/0021-release-ownership-and-final-cutover.md) мост ниже используется
для сверки исторических/переходных UUID до окончательного прекращения зарубежной
записи. Он не разрешает бессрочную работу зарубежного `lead_submit` после локализации.
Заранее подготовить российский приёмник и обработку оставшихся старых анкет.
Нельзя обещать, что уже загруженная страница сама сменит API; восстановление ввода
и остаточные обращения к старому адресу требуют отдельной проверки.

## Подготовленный перенос

`npm run migration:leads` читает все UUID исходной таблицы и сравнивает с целью.
По умолчанию обе транзакции доступны только для чтения. Для записи:

```sh
npm run migration:leads -- --apply
```

Оба URL передаются через защищённое окружение `SOURCE_DATABASE_URL` и
`TARGET_DATABASE_URL` на российском сервере. Их не помещают в командную строку,
git или журнал. Проверить адреса и направление вручную: разные адреса сами по
себе не доказывают, какая база является новой. Для источника использовать
ограниченный доступ к чтению заявок; для цели — SELECT/INSERT этой таблицы с
нужным доступом через RLS. Скрипту не нужны UPDATE/DELETE или секреты Auth.
Создание ограниченных ролей/политик — отдельное проверяемое изменение доступа,
не выполненное этим скриптом. Пока ролей нет, не объявлять доступ ограниченным.

Скрипт добавляет только отсутствующие UUID. Копирует исходную строку целиком,
включая ответы, оценку и микросекунды дат; не вызывает `lead_submit` повторно.
Существующие карточки цели не изменяет, даже если менеджер уже поменял контакт,
колонку или заметку. Проверяет схему перед записью и равенство каждой добавленной
строки. Ошибка откатывает всю партию. Повтор после потери ответа безопасен для
уже перенесённых UUID. В журнал попадают только числовые счётчики и код ошибки.

Отсутствующая на цели заявка должна быть нетронутой анкетой: `status=new`, без
заметки, автора изменения, Instagram и ручной колонки, с одинаковыми датами
создания/изменения и всеми ответами. Иначе `source-lead-needs-review` останавливает
партию: ручную работу на источнике нужно отдельно сверить, не обходить проверку.
Более 10 000 исходных строк также требует пересмотра, а не неполного копирования.

Разные UUID с одним телефоном сохраняются раздельно. Совпадение телефона не
доказывает повторную заявку; автоматическое объединение могло бы потерять ответы.
Этот мост обеспечивает повторяемость переноса UUID, но не общую дедупликацию
двух одновременно открытых API по телефону. Финансовые записи он не переносит.

## Перед переключением

1. Выполнить полное восстановление и строгую сверку; завершить/сохранить очереди.
   Ограничить старую базу для прикладных изменений, сохранив контракт анкеты.
2. В изолированной репетиции отправить анкету в старый endpoint, перенести,
   проверить исходный UUID и нужную колонку CRM. Изменить её на цели и повторить
   перенос: изменение должно сохраниться. Отозвать тестовую сессию и проверить
   запрет доступа. На настоящем лендинге фиктивные заявки не создавать.
3. На целевой площадке настроить запуск раз в минуту с контролем успешного
   завершения и оповещением об ошибках. Код/наличие таймера не доказывают работу:
   проверить журнал успешных запусков, сбой соединения и восстановление после него.
4. Выполнить начальный `--apply`, повторить проверку: `pending=0`. В финальном окне
   перевести новые сборки на проверенный российский приёмник, прекратить старую
   зарубежную запись и повторить дозагрузку/сверку уже принятых UUID. При поступлении
   реальных заявок сверять UUID и видимость в CRM. Расписание дозагрузки не является
   разрешением продолжать первичный сбор в зарубежную базу.
5. До отключения подготовить обработку оставшихся анкет и очередей; после него
   источник закрыт для клиентских записей. Срок хранения исходной копии и удаление
   регулируются отдельно. См. [критерии релиза](../release-gates.md).

Проверено локально на двух изолированных базах с настоящими миграциями: перенос
и точность дат, повтор, сохранение правок менеджера, одинаковые телефоны,
отказ при ручной работе на источнике/иной схеме, откат всей партии при ошибке.
Это не заменяет проверку сети, Auth и расписания на новом сервере.
