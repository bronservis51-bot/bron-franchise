при угрозе сроку сразу назвать конкретный блокер и продолжать независимые работы.

Актуально 13.11.2026. Один локальный исполнитель на Mac с рабочим SSH ведёт
весь серверный проход. Миграция, необходимые исправления и публикация после

между исполнителями; просить только конкретный личный вход/MFA, скрытый ввод

а не часть рабочей инфраструктуры. До завершения подтвердить аварийный доступ

остановить временный Mac-канал и проверить российские сайты/API, серверные копии
и уведомления без его участия. Постоянные таймеры, bridge или мониторинг на Mac
не допускаются. Источник сохранить; до завершения финального переноса канал
не выключать ради этой проверки.

## 1. Закрыть технический допуск

Доставить исправленный auditor, сохранить версию и результат старого завершённого
запуска. С существующей закрытой target-конфигурацией на VPS выполнить:

```sh
npm run migration:check -- --source-service
```

Перед запуском убедиться, что прежний процесс завершён. Не печатать URL/пароли,
process argv/environment, полный Compose config или строки Auth. Разбирать
расхождения по причине; учитывать дельту рабочего source, не фильтровать проверки.
Повторный импорт для исправления auditor не нужен.

После строгой сверки подтвердить оставшиеся точечные проверки: существующие роли,
свою/чужую область, анонима и отозванную сессию; Auth-триггеры, managed-совместимость,
Storage/Vault, конфигурацию и необходимые интеграции. Использовать сохранённый
metadata-архив и фактическую цель. До допуска оставить internal network,
`cron.launch_active_jobs=off`, `pg_net.batch_size=0`; definitions/active двух cron
сохранить точно. `bron-shop-worker` не включать. Старый `bron-jobs` ссылается на
удалённую подсистему: её не возвращать ради устранения ошибок; судьбу расписания
оформить отдельно перед рабочим запуском.

Главный оставшийся неизвестный — конкретный source-freeze. Установить реальные
пути записи, полномочия и проверяемый порядок остановки: REST/RPC, Auth, Storage,
фоновые процессы, прямые DB-клиенты и уже открытые транзакции. Репетировать на
изолированной цели; фактический source-freeze выполняется в финальном окне.
Read-only мигратора не ограничивает
остальных. Выключение только legacy API keys также недостаточно: действующий
лендинг использует современный publishable key. Штатные настройки доступа
проверять раньше разработки нового механизма. Сохранить административное чтение,
обратные действия и source. Источник не отключать до готовности цели/копии/отката.

## 2. Параллельно подготовить выпуск

Пока выполняются проверки допуска, готовить DNS/TLS новых имён с maintenance
или закрытым app/API, регулярную зашифрованную target-копию и одну реальную
доставку тревоги. Это не переключает пользователей со старых адресов. Production
Caddyfile сразу открывает сайты/API — для подготовки нужен закрытый вариант;
DB/Studio/pooler наружу не открывать и restore-изоляцию не снимать целиком.

Подтвердить расписание, read-back/SHA, возраст успешной копии, ёмкость 1 GB,
доступ владельца к независимому ключу и понятное восстановление. Уже выполненную
репетицию заново не повторять без причины. Использовать существующий стек и
доступный канал уведомления; не строить отдельную платформу мониторинга.
Сведения оператора/политику уточнять параллельно: они нужны для публичной анкеты,
но не запрещают независимые серверные проверки.

## 3. Провести одно финальное окно

Под подтверждённым freeze определить фактические изменения после снимка.
Не разрабатывать универсальный delta engine. Если данные уже совпадают —
не переносить их повторно. Если финальная копия проще частичного переноса,
использовать проверенное восстановление в отдельную закрытую DB/volume того же
стека с сохранением предыдущей цели и любых настоящих target-only данных.
Не создавать новые оплаченные ресурсы. Не затирать российские заявки.
`db:restore --confirm-wipe` выполняет TRUNCATE и здесь не разрешён.

Сохранить UUID/пароли, деньги по валютам, ключи повторов/версии, открытые смены,
роли, документы и принятые заявки. Выполнить финальную строгую сверку до новых
Auth-входов, затем целевой отзыв перенесённых sessions/refresh tokens и проверки
доступа. Запись после T открывается только в российской базе. Откат приложения
по возможности сохраняет эту DB; возврат source после новых записей требует
сохранения и обратной сверки дельты, не одного возврата DNS.

Публиковать проверенные production-кандидаты с российским API и целевым публичным
ключом: `app.bronservis.ru` с base `/`, переходную PWA на прежнем Pages origin
с base `/bron-franchise/`, лендинг — из его отдельного репозитория. Проверить
действительный способ публикации и ref/variables, не выполнять force push по памяти.
QA dist с `example.supabase.co`/подставным ключом не публиковать.

Для принятых старым endpoint заявок использовать существующий insert-only bridge
`migration:leads -- --source-service`: dry-run, осознанный `--apply`, затем pending=0.
Он не переносит финансы и не перезаписывает работу CRM. Очень старый JS сам API
не сменит. Неотправленная анкета сохраняется в `bron.quiz` старого origin:
реальный non-2xx отказ → обновление того же origin → восстановление → отправка
в РФ. HTTP2xx с `{ok:false}` старый JS ошибочно считает успехом и очищает черновик.
Не ставить redirect до recovery; остаточные обращения к старому адресу признать
явно. Контракт `POST /rest/v1/rpc/lead_submit`, `{p_lead:{...}}` → `{ok:true}`
сохранить; anon-чтение заявок запретить.

## 4. Подтвердить выпуск в работе

На настоящих адресах проверить прежний вход, серверные запреты, реальные заявки,
повтор/конфликт записи, старую установленную PWA/очередь/черновик и новую установку.
Проверку устройства владельца собрать в один короткий проход. Не чистить IndexedDB,
не менять владельца очереди, UUID/payload/версии/ошибки и не закрывать смены нулём.
Старый origin оставить для получения обновления и recovery.

327 тестов/CI, семь recovery-сценариев, 18 сочетаний ширины/текста и loopback
репетиция настоящего старого service worker уже выполнены. Повторять их только
при соответствующем изменении кода. Они не заменяют проверку опубликованного
поведения на устройстве и доставки в российский API. См.
[pwa-migration-queues.md](pwa-migration-queues.md).

Никаких seed/reset/wipe, фиктивных рабочих денег/заявок, смены пользовательских
паролей, удаления source, новых покупок или расширения S3-прав на delete/управление
бакетом. Секреты/дампы/PII не помещать в git, чат, логи и скриншоты.

Контрольная точка через 60–90 минут активного прохода: результат допуска,
проверяемый способ freeze, состояние параллельной подготовки и один точный блокер
при его наличии. Это бюджет проверки готовности окна, не срок релиза и не замена
проверок. При блокере продолжать независимые работы, не создавать новый общий план.
По этапам обновлять существующий checkpoint; в финале — SHA, адреса, сверки,
единственный writer, копии/тревога/откат, реальное устройство и честные ограничения.
