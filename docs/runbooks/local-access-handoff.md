# Локальный Codex на Mac: завершить перенос и рабочий релиз

Актуальное поручение владельца от **13.11.2026, Москва**. Оно заменяет прежнее «только доступ и транспорт, затем возврат в ChatGPT», включая такие ограничения в старых передачах. Локальный Codex выполняет весь согласованный перенос и доводит его до проверенного релиза. Возвращать выполнение облачному агенту и передавать команды через владельца не нужно.

Владелец разрешил миграцию, необходимые серверные настройки, исправления и публикацию после обязательных проверок. Повторное разрешение на обычные действия в этом объёме не требуется. **Дополнительные покупки запрещены.** Владелец не технический специалист: действуй самостоятельно, сообщай короткие проверенные результаты. Проси только конкретный личный вход/MFA, скрытый ввод недостающего секрета, приёмку на его устройстве или реальное изменение объёма работ. Не проси присылать SSH-ключи, пароли или токены сообщением.

## Результат и точка продолжения

Нужны работающие `https://bronservis.ru`, `https://app.bronservis.ru` и `https://api.bronservis.ru` на согласованном российском VPS, сохранённые данные и доступы, непрерывность принятых заявок, проверенный переход старых PWA, независимые копии, восстановление и доставленная тревога мониторинга. Сборка или открытие главной страницы отдельно не означают завершённый перенос.

Не начинай подготовку заново. Более свежая передача локального исполнителя сообщает следующее; подтверди её журналами и файлами на VPS:

1. Копия в Timeweb S3 прочитана обратно, SHA совпал.
2. Независимый ключ с Mac успешно расшифровал артефакт.
3. Импорт из S3 в изолированную PostgreSQL завершён одной транзакцией.
4. После перезапуска SSH-канала источник снова отвечает в read-only.
5. Строгая сверка запущена; её результат ещё не получен.
6. Определения двух cron ещё не восстановлены.
7. Публичного переключения пользователей не было.

Это отправная точка, а не указание повторить выгрузку, импорт или сверку. Сначала найди результат существующего запуска. Старые утверждения «нет копии/контейнеров/.env» не отменяют эту передачу.

## 2. Проверить существующий SSH, канал и реальный read-only SQL

Используй уже настроенный SSH с Mac, проверь fingerprint, отдельный вход и идентичность VPS (`id`, IP, hostname), без вывода секретов. Сначала на Mac:

```sh
~/.ssh/bron-source-tunnel status
```

Если канал действительно остановлен, используй существующий `start`; после разрыва повтори TLS/SQL-проверку. Не создавай второй listener. На VPS source порт должен быть только `127.0.0.1:15432`; listener сам не доказывает соединение. Пока канал нужен, Mac остаётся с открытой крышкой, питанием и интернетом.

**Не запускай старый `source-db-access.py --check/--connect`: его preflight требует отсутствия всех контейнеров.** Не удаляй восстановленные контейнеры ради этого guard. Credentials уже сохранены; повторный ввод/смена пароля без причины не нужны.

Из актуального `/opt/bron/migration` проверь защищённую конфигурацию без подключения и печати возвращаемого объекта:

```sh
node --input-type=module <<'JS'
import { sourceServiceConfig } from './scripts/migration-source.mjs';
try {
  sourceServiceConfig();
  console.log('SOURCE_CONFIG_GUARDS_PASSED');
} catch (error) {
  console.error(/^[A-Z0-9_]{3,60}$/.test(error.code || '') ? error.code : 'SOURCE_CONFIG_FAILED');
  process.exitCode = 1;
}
JS
```

Продолжай после успешного guard. Он проверяет точный service, защищённые файлы, маршрут, canonical TLS и CA. `SOURCE_DATABASE_URL`/`NODE_PG_FORCE_NATIVE` в этом режиме должны отсутствовать. Имя `bron_source` подтверждено исходниками; содержимое service/pgpass выводить не нужно. На VPS выполни реальный SQL:

```sh
env -i PATH=/usr/bin:/bin \
  PGSERVICEFILE=/root/bron-secrets/source.pg_service.conf \
  PGPASSFILE=/root/bron-secrets/source.pgpass \
  PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=30000' \
  psql -X -w -v ON_ERROR_STOP=1 --dbname='service=bron_source' <<'SQL'
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
\conninfo
SELECT current_setting('server_version') AS server_version,
       current_setting('transaction_read_only') AS read_only;
SELECT (SELECT count(*) FROM auth.users) AS auth_users,
       (SELECT count(*) FROM auth.identities) AS identities,
       (SELECT count(*) FROM storage.buckets) AS buckets,
       (SELECT count(*) FROM storage.objects) AS objects;
ROLLBACK;
SQL
```

Нужны TLS/hostname, PG17.11 и actual `read_only=on`. Session default `off` допустим при явной read-only транзакции. Прежние счётчики 16 users/16 identities/1 bucket/ 0 objects — ориентир; изменения проверять, не подгонять под старый результат.

## 3. Найти результат уже запущенной строгой сверки

Сначала процессы, units и фактические файлы на VPS. Безопасный список процессов:

```sh
ps -eo pid,ppid,lstart,etime,comm
```

Найди настоящий PID/unit по времени запуска и журналам. У живого процесса проверь направления stdout/stderr через ссылки `/proc/<найденный PID>/fd/1,2`. У найденного systemd unit проверь `ActiveState`, `SubState`, `Result`, `ExecMainCode`, `ExecMainStatus` и journal. Исчезнувший transient unit проверяй по сохранённому journal. Имена unit/log paths в репозитории не заданы — не выдумывай их. Не печатай полные process args/environment/ExecStart/history или полный Compose config: там могут быть credentials.

`scripts/migration-check.mjs` **не создаёт report.json**. Результаты:

- `Matched <n> data/schema/sequence checks...`, exit 0 — сравнение прошло.
- `Mismatch: <метки>`, exit 1 — перечисленные расхождения.
- `Migration comparison failed: <CODE>`, exit 1 — ошибка проверки/доступа.

Зафиксируй время, версию кода, безопасную итоговую строку и exit status. Не запускай второй экземпляр поверх первого. Если исходный запуск ошибся, установи причину, исправь её и только тогда обоснованно повтори на VPS:

```sh
npm run migration:check -- --source-service
```

`TARGET_DATABASE_URL` задаётся закрыто и указывает именно на изолированную цель. Source15432 и target15433 не взаимозаменяемы. Plaintext допускается только для отдельно разрешённого target loopback, не для source Supabase; общий TLS guard не ослаблять.

## 4. Разобрать расхождения без исключения неудобных проверок

Раздели метки: данные, Auth UUID/хеши паролей, схема, владельцы, grants/RLS, функции/триггеры, расширения, последовательности. Дополнительно сверь финансы отдельно по валютам и потокам, целыми минимальными единицами. Не складывай RUB/TRY/KZT без курса. CLI сравнивает полные строки, но не выводит отдельный понятный отчёт сумм по валютам.

Сопоставь время SQL snapshot, metadata supplement, импорта и проверки. Источник мог измениться после dump; отличай сохранённую дельту от ошибки восстановления. Снимки source/target независимы, поэтому финальная сверка требует окна без записи. Не исключай таблицы/поля, не меняй ожидаемые хеши и не фильтруй неудобные данные. Диагностику значений/PII оставляй закрыто на VPS.

Перед исправляющей записью проверь направление и сохрани состояние цели. Не редактируй применённые прикладные migrations; изменение оформляй новой. Не повторяй импорт без установленной причины и плана сохранения поздних изменений.

## 5. Завершить восстановление под изоляцией

Проверь фактический merge существующих Compose-файлов, runtime и port bindings. `config --quiet` безопаснее полного config с подставленными секретами. Изоляция остаётся: internal network, только DB `127.0.0.1:15433`, `cron.launch_active_jobs=off`, `pg_net.batch_size=0`. Проверь `source`, `pending_restart`, listeners и count/hash очереди pg_net до/после. Не снимай restore override целиком до допуска к внешним действиям.

Найди уже сохранённый `managed-metadata.json.zst.age` и manifest. Дополнение содержит точные managed каталоги, Auth/Storage triggers, policies/grants, managed migrations, `cron_jobs` и состояние pg_net. Используй существующий зашифрованный материал закрыто на VPS; новый export вслепую не нужен.

Строгая сверка **уже включает Storage policies/grants**. Отдельно проверь:

- Пользовательский `on_auth_user_created` на `auth.users` после появления
  `app_private.on_auth_user_created()`, без дублирования профилей/UUID.
- Точные Storage policies/grants/RLS, включая `valid_auth_session` как
  `RESTRICTIVE / ALL / authenticated`.
- Полную managed Auth/Storage совместимость columns/types/constraints/migrations,
  а не только максимум migration ID. Не применяй raw managed schema архив поверх
  инициализированных сервисов.
- Реальную версию Vault, UUID-preserving восстановление и расшифровку; расхождение
  Vault0.3.1/0.3.2 разбирать явно. Текущие Storage объекты и их bytes/SHA;
  прежние ноль объектов не гарантируют ноль перед T.
- Auth/JWT/SMTP, публичные URL/redirects, Edge и серверные интеграции.
- Два cron: точные определения и **исходные active flags**. Ожидались активный
  `bron-jobs` и выключенный `bron-shop-worker`, но обязателен фактический архив.
  Запуск запрещает runtime `cron.launch_active_jobs=off`, а не подмена flags.
  Команды cron могут содержать секреты — не выводить их в сообщения/открытые логи.

Минимально исправь найденное и перепроверь. Выключенный shop-worker автоматически не включать; внешние вызовы репетиционной копии недопустимы.

## 6. После строгой сверки проверить Auth и серверные права

Вход меняет Auth-метаданные: сначала успешная строгая сверка и фиксация baseline. На изолированной цели отзови перенесённые sessions/refresh tokens, сохранив users/identities/UUID/парольные хеши. Новый JWT secret сам не доказывает отзыв refresh tokens. На source этот шаг не выполнять.

Проверь прежний пароль, существующие роли, свою/чужую область партнёра и точки, анонима, отозванную сессию. Доказательство — RPC/RLS, а не скрытые кнопки. Реальный пароль вводит владелец лично скрыто; не менять его ради проверки. Запись/повтор/конфликт/потерю ответа, смены, деньги, документы и lead_submit проверяй на изолированной копии или с доказанным SQL rollback, без фиктивных рабочих денег/заявок. Учти последствия пробных записей/Auth-входов в финальном образе; изменённая репетиционная копия сама не равна source.

## 7. Единое окно: freeze, вся дельта, старые формы и PWA

Подготовь российский приёмник, совместимые сборки и защиту новых записей цели. Зафиксируй момент T и единственную рабочую БД после него. Проверь все пути записи: CRM/финансы/знания, Auth/Storage, cron/Edge и интеграции. Готового полного source-freeze helper в ветке нет. Read-only подключение мигратора не замораживает остальных клиентов; одного запрета денежных RPC мало. Способ ограничения managed Auth/Storage ещё требует проверки реальных прав. Не обходи отказ managed-схем и не ставь фиктивную отметку.

Подготовь минимальный исполняемый freeze по фактическим путям/полномочиям, проверь отказ старых записей, уже открытые транзакции и фоновые процессы. Сохрани обратные действия и контроль новых данных. Source не удалять. Если безопасный freeze недоступен, назови конкретный незакрытый путь и нужное действие; публичное переключение до решения запрещено.

Под freeze сохрани всю дельту после снимка: открытые смены, финансы/версии/ключи повторов, роли/назначения, документы, знания, Auth/Storage и заявки. Выбери минимальный проверяемый способ по фактической дельте. Чистая финальная копия после ограничения записи допустима как обоснованный финальный этап, если это проще и надёжнее частичного переноса; это не повтор репетиции вслепую. До restore отдельно защити уже принятые на цели данные. **Не затирай российские заявки и новые рабочие записи финальным импортом.** После финальной строгой сверки вновь примени необходимые target session revocations перед открытием; ожидаемое изменение Auth-метаданных фиксируй отдельно.

Для уже принятых старым endpoint анкет готов insert-only bridge:

```sh
npm run migration:leads -- --source-service
npm run migration:leads -- --source-service --apply
npm run migration:leads -- --source-service
```

Сначала dry-run, затем осознанный apply в правильную цель, затем `pending=0`. UUID/точные даты сохраняются, правки CRM на цели не перезаписываются, ручная работа source требует отдельного разбора. Bridge не переносит финансы. Проверь реальные ограниченные права, расписание и контроль ошибок; source-service сам не означает наличие ограниченной DB-роли.

Для **неотправленных** старых форм уже есть опора в лендинге `fb5210c`: input/change сохраняют поля в localStorage `bron.quiz`, `restore()` поднимает их при открытии анкеты, ошибочная отправка ключ не удаляет. Проверь синтетический переход: отказ старого endpoint → сохранённые поля → обновление **того же старого Pages origin** на сборку российского API → восстановление анкеты → отправка в РФ. При закрытии старого endpoint нужен настоящий HTTP-отказ: старый JS считает любой 2xx успехом и удаляет `bron.quiz`, даже не проверяя `{ok:false}`. Новый origin старый localStorage не читает. Не ставь redirect до восстановления ввода; отдельно проверь отказ localStorage и ещё не сохранённый ввод. Используй mock API, а не фиктивную рабочую заявку.

У уже загруженного JS адрес Supabase фиксирован: DNS/новый HTML его не изменят. После T нельзя скрыто оставлять бессрочный сбор в США. Запрет вставок также не доказывает отсутствие остаточных передач по старому адресу. Если для конкретной очень старой формы полностью прозрачный переход невозможен, покажи проверенный предел и один конкретный вариант действия владельца до T. Не обещай невозможного.

PWA нужны две совместимые сборки с российским API: новая `app.bronservis.ru` с base `/` и переходная на прежнем `https://bronservis51-bot.github.io/bron-franchise/` с base `/bron-franchise/`. Старая иконка сохраняет прежний origin. Не ослабляй guard обновления, не очищай IndexedDB, не меняй владельца очереди, UUID/payload/версии/ошибки, не закрывай смены нулём. Проверь получение нового JS после закрытия вкладок/нового открытия и входа тем же UUID. Recovery/import не означает серверное сохранение до его проверки.

## 8. Опубликовать сайты, DNS и HTTPS на существующем стеке

**Облачные dist/QA build собраны с `example.supabase.co` и синтетическим ключом. Лендинг — из существующего отдельного репозитория, без изменения оформления и сценариев. Обнови API URL/публичный ключ и метаданные домена. Используй существующие `docker/bron/site/app/` и `docker/bron/site/landing/` по реальным volume mounts; не копируй `.git`, внутренние документы и секреты.

## 9. Подтвердить копии, мониторинг и откат с новыми данными

Не создавай новые платные ресурсы, платформы или зависимости ради удобства. Проверь существующие S3 helpers, политики, расписания и журналы; недостающее выполни штатными средствами действующего VPS. Серверному S3-пользователю не выдавать delete/управление бакетом. Независимый ключ не складывать вместе с копией; постоянный SSH-ключ Mac не передавать в чат/VPS.

Подтверди регулярную зашифрованную копию рабочей цели, read-back/SHA, возраст последнего успеха, реальное расписание и ёмкость в оплаченных 1 GB. Сохрани доказательство уже выполненной проверки независимого ключа; без причины не повторяй её. Владелец должен иметь понятный доступ к аварийному восстановлению. Объём/хранение измеряются: не покупай расширение и не урезай хранение молча. Исходник автоматически не удаляется.

Проверь HTTP/Auth/API, диск/память/контейнеры, ошибки и возраст копий. Скрипт или таймер не доказывают мониторинг: безопасным контролируемым сбоем подтверди доставку уведомления по согласованному доступному каналу и возврат нормального состояния. Не выдумывай получателя/контакт/круглосуточного дежурного. Если личное подключение отсутствует, попроси одно конкретное действие.

Сохрани понятные действия восстановления/отката, измеренные время и возможную потерю данных. После первых записей в РФ откат начинается с сохранения/сверки новой дельты: DNS назад или старый dump её потеряют. По возможности откатывай совместимую сборку, сохраняя текущую DB; обратный перенос данных требует проверки направления, UUID, повторов и финансов.
