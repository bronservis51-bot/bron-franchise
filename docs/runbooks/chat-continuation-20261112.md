## Точная точка продолжения

Сначала проверить текущие процессы на VPS, listener канала, наличие и содержание
manifest в `/var/backups/bron-franchise/source-*`. Не повторять дамп вслепую,
не объединять части разных snapshot и не удалять частичные/успешные копии.

Рабочий driver находится здесь:
`/opt/bron/migration/deploy/timeweb/source-backup.py`.
Его проверенный SHA-256:
`94c4a9411db6085ac18daae0fd18e7a5f14f2c9a82adb256e39f73039121f75d`.
На VPS распакован пакет коммита `8f630e77e846f7a0182ad7266ba228bcaf62d284`.
Старый `/root/f` содержит предыдущую версию; его не использовать как актуальный.
На новом driver прошли `--tunnel --diagnose-keeper`, `--tunnel --diagnose-managed`
и затем `--tunnel --backup`. Истинная причина прежних таймаутов окончательно
не доказана; успешный повтор не доказывает конкретное объяснение сбоя.

Проверка доступа на VPS при необходимости:
`python3 /opt/bron/source-db-access.py --tunnel --connect`.
Host fingerprint, сверенный через доверенную VNC:
`SHA256:8KA0F5NRZo8hIn84yT/pSclefFxk8zRg9JzuPuilYh0`.
Не принимать новый ключ автоматически. На Mac управление каналом:
`~/.ssh/bron-source-tunnel status|start|stop`. Mac нужен включённым, с открытой
крышкой, питанием и интернетом до завершения работ с источником через этот канал.
Основную миграцию выполнять здесь; локальный Codex использовался только для доступа.

После проверки артефактов последовательно:

1. Дополнить копию конфигурацией Auth/JWT/SMTP, Edge Functions/секретами,
   Storage и Vault; проверить независимое хранение ключа расшифровки.
   Ключ age сейчас `/root/bron-secrets/source-backup.agekey`; не печатать его.
2. Завершить ограниченный S3-доступ без удаления/управления бакетом, загрузку
   зашифрованной migration-копии, read-back SHA и расписание регулярных копий.
   Измерить объём; 504 KiB относились к частичным файлам и не доказывают, что
   политики хранения хватит в 1 GB. Имена объектов уникальные; NoDelete не
   защищает от перезаписи. Основной S3-ключ не сохранять на VPS; age identity
   не складывать вместе с копиями. Если потребуются новые чувствительные
   полномочия, объяснить конкретную необходимость и пределы доступа.
3. Провести изолированное восстановление по `restore-rehearsal.md`.
   Restore override ещё не применён. До первого старта: internal network,
   только target DB `127.0.0.1:15433`, `cron.launch_active_jobs=off`,
   `pg_net.batch_size=0`; проверить реальные runtime settings. Это отдельный
   порт от исходного канала 15432. Сначала DB, затем указанные Auth/Storage

4. Выполнить строгую сверку до пробных входов:
   `npm run migration:check -- --source-service`. Source service сохраняет
   canonical TLS; target URL задаётся закрыто. Node/зависимости и этот режим
   ещё не проверены на VPS. Сверить значения/UUID/хеши паролей, права, деньги
   по валютам, расширения, файлы; затем проверить реальные роли и входы.
5. Завершить PWA recovery/update и freeze источника, российский приёмник
   заявок и late-leads bridge. Подготовить финальную дельту и проверяемый откат.
6. После допуска — финальная сверка, отзыв перенесённых sessions/refresh tokens
   только на цели, HTTPS/DNS/сборки обоих сайтов, проверки старой/новой PWA,
   реального входа без VPN, резервирования и тревог. Источник не удалять
   автоматически после появления новой страницы.

## Обязательные ограничения

- Никаких новых покупок, autoscaling, смены тарифа, seed/reset/wipe,
  демо-аккаунтов и тестовых денег/заявок в рабочей базе.
- Контракт лендинга сохраняется: `POST /rest/v1/rpc/lead_submit`,
  `{ "p_lead": { ... } }`, ответ `{ "ok": true }`. Anon может отправлять,
  но не читать заявки. Старые открытые формы требуют отдельного решения;
  финальный restore не должен затирать лиды, уже принятые российской целью.
- Не очищать IndexedDB/очередь и не ставить безусловный redirect со старого
  origin `/bron-franchise/` до доставки ожидающих записей. Export/recovery/import
  и исполняемый полный freeze источника остаются незавершёнными.
- БД/Studio/pooler наружу не открывать; TLS-проверку не отключать. Секреты и
  персональные данные не копировать в git, чат, логи, frontend или скриншоты.
- Cron/pg_net/Edge не должны выполнять внешние действия на репетиционной копии.
  Выключенный `bron-shop-worker` не включать автоматически.
- Стек уже закреплён: Supabase upstream
  `0ed90ae4603ff58f6e170fed51ea23bbda11cf6f`, gateway Envoy `api-gw`,
  PostgreSQL `17.11.0.019` по digest из override. Не применять старые Kong
  инструкции или `latest`. Совместимость Vault 0.3.1/0.3.2 и Auth/Storage
  проверить на реальном восстановлении, а не предполагать по исходникам.
