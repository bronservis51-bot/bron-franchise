# Копии, восстановление и полный перенос

Текущее исполнение переноса, смета, доступы и критерии переключения:
[перенос в РФ](russia-migration.md). Это отдельный процесс от прикладного JSON restore.

Служебные DB-подключения используют `scripts/database-config.mjs`: TLS проверяет
сертификат и имя сервера, свой CA задаётся через `BRON_DB_CA_FILE`. Параметр
`sslmode=require` не отключает проверку. Для заранее настроенного SSH-туннеля
допустим только loopback URL с `sslmode=disable` и явным
`BRON_DB_ALLOW_LOCAL_PLAIN=1`; удалённый незашифрованный адрес запрещён.
Не подменять исправление сертификата настройкой `rejectUnauthorized:false`.

Облачная база не является резервной копией. Не считать наличие Free-проекта,
скрипта или файла выгрузки доказательством, что восстановление проверено.
Резервные данные содержат персональные сведения и секретные Auth-материалы;
хранить вне git с ограничением доступа, при выбранной схеме локализации — в РФ.

## Прикладная копия

Перед изменением рабочей БД и после значимого импорта запускать `npm run db:export`
с секретами в защищённом окружении администратора. Для текущей эксплуатации
нужны также регулярные автоматические копии и проверка их восстановления;
расписание не объявляется настроенным по наличию скрипта.

Результат — `backups/<время>/data.json` и `files/`. Выгрузка содержит таблицы
приложения, сведения Auth, приватные снимки поставок и служебные финансовые записи.
Она чувствительна, в том числе из-за хешей паролей. Файлы перечисляются по
`partner_document` и скачиваются из закрытого `private-files`. При наличии файлов
нужны `VITE_SUPABASE_URL` и серверный `SUPABASE_SECRET_KEY`; ошибка выгрузки или
отсутствие ключа не дают считать копию полной. Промежуточный `data.json` может уже
существовать после неуспеха команды — это ещё не успешная копия всего проекта.

## Прикладное восстановление JSON

`npm run db:restore -- <каталог-копии> --confirm-wipe` заменяет бизнес-данные
**целевого** проекта. Использовать только на подготовленной изолированной цели с
нужными миграциями и пользователями, после проверки адреса. Пользователи
сопоставляются по email; их UUID на цели могут отличаться. Наличие `auth_users`
в копии не означает, что этот restore восстанавливает Auth и пароли целиком.
Не создавать настоящих пользователей скриптом синтетических `seed:users`.

Файлы восстанавливаются отдельно от транзакции бизнес-данных; проверить наличие
серверного ключа, число объектов, контрольные суммы и открытие документов. Одного
сообщения об успешной транзакции БД недостаточно. SQL-тест восстановления
`tests/db/backup.test.ts` не заменяет полную репетицию с Auth и хранилищем.

## Полный перенос рабочей системы

Для первого этапа SQL/Auth подготовлен
[source-backup.py](../../deploy/timeweb/source-backup.py). Только на проверенном
российском VPS с уже созданными root/0600 service/pgpass и сверенным файлом:

```sh
python3 source-backup.py --tunnel --check
python3 source-backup.py --tunnel --prepare-key
python3 source-backup.py --tunnel --backup
```

`--check` проверяет локальные ограничения, CA, PG17.11/CLI3.1.0 и точные хеши
официальных dry-run сценариев; источник не запрашивается. CLI видит только dummy
URI, реальные credentials потребляет нативный libpq. `--prepare-key` создаёт либо
переиспользует `/root/bron-secrets/source-backup.agekey`, не печатая ключ.
Его независимое хранение и способ восстановления ещё требуется подтвердить.

`--backup` держит экспортированный read-only snapshot и применяет его ко всем
`pg_dump`. Roles-only и последовательности не входят в общий MVCC-снимок, поэтому
финальное окно без изменений остаётся обязательным. Vendor roles/schema/data,
нефильтрованный архив схемы, managed migration versions и raw/logical Vault
передаются непосредственно через zstd→age в закрытый каталог
`/var/backups/bron-franchise/source-*`; plaintext на диск не записывается.
Сбой producer/compressor/encryptor/keeper не публикует manifest успеха.

**Этот этап всегда `complete=false`.** Storage bytes, конфигурация Auth/JWT/SMTP,
функции/секреты, независимое S3, хранение ключа и пробное восстановление ещё не
подтверждены. Raw schema/managed versions — архив для разбора, не SQL для слепого
применения. Logical Vault нужен для проверенного повторного шифрования с
сохранением UUID; это не утверждение о готовом byte-exact cryptographic restore.
Наличие driver и 34 offline-тестов не доказывает реальную выгрузку.

Исполнение 12.11: driver из `5201bbb6380b5620e463530690c2d3ac2546359b`
загружен как `/root/f`; SHA-256
`e5ab158d6ea4290f00141913fa401154553075ed5008b35aa1796bad337b941a`
совпал. На VPS `--tunnel --check` прошёл, в том числе проверку реального CLI

Общий `database-config.mjs` не ослабляется. Node/зависимости и реальный запуск
этого режима на VPS ещё не подтверждены; профильные offline TLS-тесты прошли.

Порядок изоляции и freeze до первого старта цели:
[restore-rehearsal.md](restore-rehearsal.md). Его Compose override ещё не применён.

Для сохранения пользователей, UUID и паролей при переходе platform → self-hosted
использовать актуальную [официальную процедуру Supabase](https://supabase.com/docs/guides/self-hosting/restore-from-platform),
а не прикладной JSON restore. Переносятся роли, схема и данные, включая Auth;
JWT/API secrets, настройки Auth, SMTP, DNS и файлы требуют отдельной настройки.
Объекты хранилища копируются по [отдельной инструкции](https://supabase.com/docs/guides/self-hosting/copy-from-platform-s3).
Совместимость версий PostgreSQL/Auth/Storage проверить на пробном экземпляре.

После восстановления выполнить `npm run migration:check`, передав
`SOURCE_DATABASE_URL` и `TARGET_DATABASE_URL` только через защищённое окружение.
Это проверка без записи в согласованных снимках: все таблицы приложения и
приватной схемы, Auth users/identities (включая UUID и хеши паролей), редакции знаний,
назначения, выручка, заявки, роялти, поставки, метаданные документов, определения
RPC/RLS/grants, владельцы объектов, индексы, ограничения и последовательности,
прикладные триггеры, колонковые права, версии расширений и Storage metadata/policies/grants.
Сверяются значения, а не только число строк. Пустая/неполная схема не проходит.
Сверка выполняется до пробных входов, меняющих Auth-метаданные, и в окне без
изменений данных; поступающие лиды требуют отдельного учёта. Содержимое файлов,
настройки Auth и SMTP, расширения, отозванные сессии и работоспособность проверять отдельно.
Дополнительно проверить входы, RLS/RPC и временные ссылки на документы.

Новые ключи означают повторный вход пользователей; старые сессии не должны стать
действующими на цели. До переключения завершить/сохранить очереди и учесть записи,
пришедшие во время копирования. Заявки лендинга не останавливать. Полный порядок
и откат с учётом новых записей описаны в [rollout-plan.md](../rollout-plan.md).

## Регулярная эксплуатация

На новой площадке назначить ответственного за копии и восстановление, срок
хранения, шифрование, независимое хранилище и проверку ошибок. Цели RPO ≤ 1 ч и
RTO ≤ 4 ч остаются целями до настройки и измеренной репетиции; один VPS и
ручной JSON-экспорт их не обеспечивают. Для PostgreSQL рассмотреть WAL/PITR;
для файлов нужен согласованный отдельный порядок резервирования.

### Timeweb S3: подготовленные правила

12.11.2026 через панель Timeweb сохранены и прочитаны обратно три правила
Expiration: `hourly/` — 1 день, `daily/` — 30 дней, `monthly/` — 366 дней.
Перед изменением панель объектов показывала «Папка пуста», lifecycle отсутствовал,
versioning и Object Lock были отключены. Для `migration/` правил нет.
Multipart abort из JSON-кандидата **не применён**, IAM-политика не применена;
пользователь, ключи, загрузчик, расписание и восстановление ещё не настроены.
Факт применения Expiration не подтверждает работу автоматического копирования.
Используется
существующий приватный `bron-franchise-backups`, endpoint
`https://s3.twcstorage.ru`, регион `ru-1`, фиксированный тариф 1 GB.
Автомасштабирование и увеличение оплаты не включать.

[backup-uploader-policy.json](../../deploy/timeweb/backup-uploader-policy.json) —
IAM-политика отдельного дополнительного пользователя, **не bucket policy**;
`Principal` отсутствует. В панели у пользователя должны быть «Нет доступа» ко
всем бакетам; готовый preset «Чтение и запись» включает удаление. Основной S3
администратор не используется загрузчиком и его ключ не хранится на VPS.
Политика разрешает PUT/GET только внутри `hourly/`, `daily/`, `monthly/`,
`migration/`; HEAD проверяется через GetObject. ListBucket раскрывает имена
всех объектов только этого отдельного backup-бакета: условный prefix-listing
не используется без подтверждения поддержки Timeweb. Вне четырёх префиксов
нет доступа к содержимому. Явные Deny запрещают DeleteObject/DeleteObjectVersion,
перечисленные изменения ACL/бакета и HTTP даже при дополнительных Allow.
Корректное имя IAM-действия для lifecycle — `s3:PutLifecycleConfiguration`.
Перед использованием проверить фактически прикреплённую политику и отсутствие
дополнительных разрешений/публичных ACL. Отказ удаления проверять только на
одноразовом неперсональном probe-объекте, не на резервной копии; управление
бакетом не проверять попыткой его удаления или смены рабочей policy.

NoDelete **не запрещает перезапись** через PutObject и не отменяет lifecycle.
Каждому запуску нужен уникальный UTC timestamp/UUID в ключе; существующий ключ
не заменять, `sync --delete` не использовать. После проверенного восстановления
можно отдельно убрать `migration/*` из PUT, сохранив GET, чтобы серверный ключ
не мог перезаписывать зафиксированную копию. ACL-заголовки не передавать.
Начальный uploader должен использовать single PUT и read-back SHA-256;
Multipart list/abort permissions не предоставлены. Загрузчик ещё не написан.
Загружать только зашифрованные age-артефакты и проверенный metadata manifest;
identity age, pgpass и S3 secret key не помещать в этот бакет. Проверку
сертификата HTTPS не отключать.

[backup-lifecycle-unversioned.json](../../deploy/timeweb/backup-lifecycle-unversioned.json)
предназначен **только для бакета, где versioning никогда не включали**:

| Префикс | Истечение полных объектов | Незавершённые multipart |
| --- | --- | --- |
| `hourly/` | 1 день | Прервать через 1 день |
| `daily/` | 30 дней | Прервать через 1 день |
| `monthly/` | 366 дней | Прервать через 1 день |
| `migration/` | Правил нет, автоматически не удалять | Правил нет |

366 дней — консервативное временное окно, учитывающее високосный год; это не
календарные 12 месяцев и не гарантия ровно 12 объектов. Lifecycle работает с
возрастом, а не числом копий; 1/30/366 дней сами по себе не обеспечивают ровно
24 часовых/30 дневных/12 месячных точек. Нужны успешное расписание, контроль
разрывов и фактическое подтверждение очистки. Timeweb не задаёт точного момента
обработки правил — ожидаемое удаление не считать уже освобождённым местом.
Lifecycle не проверяет восстановимость и наличие более новой успешной копии:
последняя регулярная точка тоже истечёт по возрасту при длительном сбое копирования.

До применения прочитать и сохранить текущие lifecycle/versioning/policy/ACL.
PUT lifecycle заменяет конфигурацию целиком: нельзя потерять чужие правила или
оставить глобальное правило с пустым Filter, которое удалит `migration/`.
При Enabled **или Suspended** эту конфигурацию не включать без отдельного
разбора старых версий: Expiration не очищает noncurrent versions. Версионирование
занимает место, после включения может только приостанавливаться; автоматически
не включать его или Object Lock. Миграционную копию не удалять до репетиции,
сверки и отдельно определённого срока хранения.

Для 1 GB до каждой загрузки измерять занятое место и размер новой партии,
учитывать migration, версии и multipart; оставлять резерв и оповещать заранее
(предлагаемый порог — 80% подтверждённой квоты, не гарантия достаточности).
При нехватке остановить новую загрузку и сообщить факт; не удалять проверенные
копии и не увеличивать тариф автоматически. При выключенном autoscaling
достижение тарифного лимита Timeweb приостанавливает сервис и операции с бакетом.
Перед первой загрузкой регулярных копий проверить ёмкость и независимую
migration-копию чтением и восстановлением в РФ; уже сохранённые expiry действуют
только на три регулярных префикса, а не на migration.

Подготовлен [source-s3-policy-bootstrap.py](../../deploy/timeweb/source-s3-policy-bootstrap.py),
11 offline-тестов. Доставлен в составе пакета в `/opt/bron/migration`, но не
запускался; fixed policy path и SDK на VPS ещё не подготовлены. По умолчанию только `--check`,
без сети/импорта SDK. Применение требует отдельного согласия на разовое
использование основного S3-ключа в RAM проверенного российского VPS и создания
ограниченного пользователя. Вход ключа скрыт в TTY; env/argv/файлы его не содержат,
core dump выключен, при активном swap скрипт отказывает до ввода. Используется
только IAM PutUserPolicy и попытка GetUserPolicy на фиксированном TLS endpoint,
без redirect/retry. Загрузчик/копии/ключи этим скриптом не создаются.
Имя дополнительного IAM-пользователя сверить с фактическим S3 ID после создания:
если `bron-franchise-backup` является только комментарием, не применять текущий
фиксированный USERNAME; сначала подготовить и проверить точный идентификатор.
Даже успешный read-back не подтверждает GET/PUT и отказ DELETE: они требуют
проверки отдельными одноразовыми неперсональными probe-объектами.
