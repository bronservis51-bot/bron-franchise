# Копии, восстановление и полный перенос

Облачная база не является резервной копией. Не считать наличие Free-проекта,
скрипта или файла выгрузки доказательством, что восстановление проверено.
Резервные данные содержат персональные сведения и секретные Auth-материалы;
хранить вне git с ограничением доступа, при выбранной схеме локализации — в РФ.

## Прикладная копия

Перед изменением рабочей БД и после значимого импорта запускать `npm run db:export`
с секретами в защищённом окружении администратора. Для текущей эксплуатации
нужны также регулярные автоматические копии и проверка их восстановления;
расписание не объявляется настроенным по наличию скрипта.

Результат — `backups/<время>/data.json` и `files/`. Выгрузка содержит таблицы
приложения, сведения Auth, приватные снимки поставок и служебные финансовые записи.
Она чувствительна, в том числе из-за хешей паролей. Файлы перечисляются по
`partner_document` и скачиваются из закрытого `private-files`. При наличии файлов
нужны `VITE_SUPABASE_URL` и серверный `SUPABASE_SECRET_KEY`; ошибка выгрузки или
отсутствие ключа не дают считать копию полной. Промежуточный `data.json` может уже
существовать после неуспеха команды — это ещё не успешная копия всего проекта.

## Прикладное восстановление JSON

`npm run db:restore -- <каталог-копии> --confirm-wipe` заменяет бизнес-данные
**целевого** проекта. Использовать только на подготовленной изолированной цели с
нужными миграциями и пользователями, после проверки адреса. Пользователи
сопоставляются по email; их UUID на цели могут отличаться. Наличие `auth_users`
в копии не означает, что этот restore восстанавливает Auth и пароли целиком.
Не создавать настоящих пользователей скриптом синтетических `seed:users`.

Файлы восстанавливаются отдельно от транзакции бизнес-данных; проверить наличие
серверного ключа, число объектов, контрольные суммы и открытие документов. Одного
сообщения об успешной транзакции БД недостаточно. SQL-тест восстановления
`tests/db/backup.test.ts` не заменяет полную репетицию с Auth и хранилищем.

## Полный перенос рабочей системы

Для сохранения пользователей, UUID и паролей при переходе platform → self-hosted
использовать актуальную [официальную процедуру Supabase](https://supabase.com/docs/guides/self-hosting/restore-from-platform),
а не прикладной JSON restore. Переносятся роли, схема и данные, включая Auth;
JWT/API secrets, настройки Auth, SMTP, DNS и файлы требуют отдельной настройки.
Объекты хранилища копируются по [отдельной инструкции](https://supabase.com/docs/guides/self-hosting/copy-from-platform-s3).
Совместимость версий PostgreSQL/Auth/Storage проверить на пробном экземпляре.

После восстановления выполнить `npm run migration:check`, передав
`SOURCE_DATABASE_URL` и `TARGET_DATABASE_URL` только через защищённое окружение.
Это проверка без записи: UUID/хеши пользователей, назначения, выручка, заявки,
роялти, поставки и метаданные документов. Содержимое файлов проверять отдельно.
Дополнительно проверить входы, RLS/RPC и временные ссылки на документы.

Новые ключи означают повторный вход пользователей; старые сессии не должны стать
действующими на цели. До переключения завершить/сохранить очереди и учесть записи,
пришедшие во время копирования. Заявки лендинга не останавливать. Полный порядок
и откат с учётом новых записей описаны в [rollout-plan.md](../rollout-plan.md).

## Регулярная эксплуатация

На новой площадке назначить ответственного за копии и восстановление, срок
хранения, шифрование, независимое хранилище и проверку ошибок. Цели RPO ≤ 1 ч и
RTO ≤ 4 ч остаются целями до настройки и измеренной репетиции; один VPS и
ручной JSON-экспорт их не обеспечивают. Для PostgreSQL рассмотреть WAL/PITR;
для файлов нужен согласованный отдельный порядок резервирования.
