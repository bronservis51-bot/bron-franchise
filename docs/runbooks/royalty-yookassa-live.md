# Рабочие счета роялти в ЮKassa

Серверный обработчик выставляет одноразовый счёт по ссылке в магазине «Франшиза», когда подключённый франчайзи нажимает «Оплатить». В описание попадают имя франчайзи, месяц и год роялти и просьба проверить данные. Сумма сверяется с начислением. Адрес для чека берётся из поля контактного email в карточке партнёра и сохраняется для повторов вместе со ShopID и именем франчайзи.

Рабочий ключ получает отдельный шлюз. Для обработчика доступны только создание одноразового счёта и чтение счёта или платежа через закрытый Unix-сокет. Шлюз сверяет ShopID и блокирует операции вне этого списка. Сверка возврата читает сумму из статуса платежа. Реальные возвраты оформляют уполномоченные сотрудники в личном кабинете ЮKassa.

## Проверка магазина без выставления счёта

Запишите `YOOKASSA_LIVE_SHOP_ID` и `YOOKASSA_LIVE_SECRET` магазина «Франшиза» защищённой командой ввода на рабочем VPS. Она проверяет существующую оплаченную операцию и сохраняет ключ в файле шлюза. После установки шлюза выполните такую же проверку через его Unix-сокет под пользователем обработчика. Для этой команды передайте только ShopID и ID существующей операции.

```sh
runuser -u bron-royalty-invoice -- env -i BRON_YOOKASSA_MODE=invoice_live \
  YOOKASSA_LIVE_SHOP_ID="$SHOP_ID" /opt/bron/node-v22.23.5-linux-x64/bin/node \
  scripts/royalty-yookassa.mjs --verify-payment "$EXISTING_PAYMENT_ID"
```

## Развёртывание

1. Зафиксируйте ревизию приложения и рабочей базы. Выполните [порядок обновления приложения](deploy.md), включая закрытую копию перед миграциями и проверку штатных ролей после обновления. На этом этапе оставьте список подключённых к рабочему магазину партнёров пустым.
2. Создайте системных пользователей `bron-royalty-invoice` и `bron-royalty-gateway` с разными UID и группами. Разместите код и зависимости закреплённой ревизии в `/opt/bron/royalty-invoice`, а единственный скрипт шлюза в `/opt/bron/royalty-gateway`. Оба каталога принадлежат root. Для обработчика нужен Node.js 22+ и `pg` из lock-файла. Используйте `npm ci --include=dev`, поскольку `pg` объявлен в devDependencies.
3. Владелец БД создаёт отдельную роль для обработчика. В примере роль называется `bron_royalty_invoice`. Пароль устанавливается защищённым способом. Выдайте `CONNECT` только к нужной БД и следующие права на очередь.

   ```sql
   grant usage on schema app_private to bron_royalty_invoice;
   grant execute on function app_private.royalty_live_invoice_checkout_work(integer,text),
     app_private.royalty_live_invoice_checkout_observe(uuid,uuid,text,text,text,date,uuid,bigint),
     app_private.royalty_live_refund_work(integer,text),
     app_private.royalty_live_refund_observe(uuid,uuid,uuid,bigint) to bron_royalty_invoice;
   ```

   При обновлении рабочего обработчика сначала остановите старый таймер и завершите старый процесс. Уберите выданное ранее право на `app_private.royalty_checkout_observe(uuid,uuid,text,text,text,date)` у рабочей роли. Новый процесс проводит запись и сохраняет ID платежа и подтверждённую сумму возврата одной транзакцией.

4. Храните рабочий ключ магазина в `/etc/bron-franchise/royalty-invoice.env` с владельцем root и режимом `0600`. Служба обработчика получает отдельный файл `/etc/bron-franchise/royalty-invoice-worker.env` с теми же правами. Укажите в нём `BRON_YOOKASSA_MODE=invoice_live`, тот же ShopID и `BRON_ROYALTY_LIVE_DATABASE_URL` выделенной роли. Для соединения обязательна проверка TLS. На VPS с PostgreSQL в Docker задайте `BRON_ROYALTY_DB_IP` с фактическим частным IPv4 из сертификата PostgreSQL и `BRON_DB_CA_FILE` с путём к проверенному сертификату или ЦС. В конфигурации systemd обработчика разрешите этот адрес как отдельное правило `IPAddressAllow=<IP>/32`. Сохраните основное правило `IPAddressDeny=any`. Для подключения через loopback отдельное правило адреса не требуется.
5. Установите службы и сокет шлюза `bron-royalty-gateway.{socket,service}`, службу обработки и её таймер `bron-royalty-invoice.{service,timer}` из `deploy/timeweb/`. Проверьте их командой `systemd-analyze verify` и перечитайте конфигурацию systemd. Сокет доступен группе обработчика. Проверьте блокировку операций по тестам шлюза с имитацией ЮKassa и доступ к магазину по одной существующей операции. Выполните один запуск обработчика с пустым списком подключений. Включайте таймер после проверки соединения с БД, границы доступа и готовности выпуска.
6. Для первого подключения сверьте карточку выбранного франчайзи, email доставки чека и порядок зачёта предоплаты в используемой онлайн-кассе. Подключите его UUID и подтверждённый ShopID параметризованным запросом владельца БД. Для активации берутся действующие франчайзи с учётом в RUB. За каждым франчайзи остаётся текущий расчёт суммы в кабинете.

   ```sql
   insert into app_private.royalty_checkout_pilot(partner_id,use_invoice,invoice_shop_id)
   values ($1::uuid,true,$2::text)
   on conflict (partner_id) do update
   set use_invoice=excluded.use_invoice,invoice_shop_id=excluded.invoice_shop_id;
   ```

## Контроль после включения

- Проверьте запись в списке счетов ЮKassa для первой выставленной партнёром суммы. После фактической оплаты проверьте доставку чека прихода и одну запись в журнале. При регулярных сверках проверяйте статус регистрации чеков по оплаченным счетам в ЮKassa. Зачёт предоплаты проводится по действующей процедуре магазина. [Чеки по счетам ЮKassa](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/invoices/receipts)
- Для остановки выставления уберите франчайзи из списка подключения. Уже выданные ссылки действуют до окончания срока или подтверждённой отмены в ЮKassa. Оставьте обработчик включённым до сверки ранее созданных счетов.
- До первого подключения партнёра сверьте неоплаченные ручные счета за тот же месяц в ЮKassa. После восстановления базы сверяйте выставленные счета, оплаты и возвраты с момента резервной копии до возобновления выставления.

## Ручная отметка и корректировка

1. В диалоге оплаты или исправления начисления выберите месяц и приостановите онлайн-оплату перед приёмом наличных, отдельным переводом или изменением суммы. Приложение скроет ссылку и не выставит новый счёт на паузе.
2. Если счёт ещё выставлен, отмените его в разделе «Счета клиентам» рабочего магазина ЮKassa и дождитесь статуса «Счёт больше нельзя оплатить» в кабинете франшизы. Пока состояние неизвестно или старый счёт ещё можно оплатить, запись денежного поступления и изменение начисления блокируются на сервере. [Отмена счёта в личном кабинете](https://yookassa.ru/docs/support/merchant/invoices-to-clients/invoice-history)
3. Отметьте фактически полученные наличные или прямой перевод либо исправьте начисление. Когда ЮKassa уже провела оплату, отдельное поступление укажите со способом и номером платёжного документа. Выписка о перечислении денег ЮKassa на ваш счёт относится к исходной оплате. Если обе оплаты уже произошли, сверьте их до того, как решать вопрос с переплатой. Сохраните паузу до окончания сверки и возобновите онлайн-оплату, когда можно выставлять счёт за оставшийся долг.
4. Проведённые возвраты ЮKassa сверяются запросами на чтение. Исходная оплата остаётся в истории, сумма возврата видна рядом, долг пересчитывается по чистой сумме. Рабочий обработчик получает возвраты из ЮKassa после оплаты и при последующих проверках. Выгрузка операций сохраняет сумму и дату исходного поступления и указывает накопленный возврат в примечании. Дату каждого возврата сверяйте по реестру ЮKassa. [Реестры](https://yookassa.ru/developers/payment-acceptance/after-the-payment/reports)

## Восстановление после потери ответа

Первые 23 часа обработчик повторяет создание с идентификатором той же попытки, пока онлайн-оплата за этот месяц не поставлена на паузу. После этого попытка остаётся на проверке. Код HTTP в журнале сервиса помогает различить ошибку авторизации, ошибку запроса и недоступность API. Ответы ЮKassa и реквизиты в журнал не записываются.

1. Владелец рабочей БД находит открытую попытку по партнёру, месяцу и магазину в `app_private.royalty_checkout_attempt`. Сверьте сумму и UUID попытки из `metadata.royalty_attempt_id` с ЮKassa. Если счёт найден, возьмите его идентификатор `in-<uuid>` и передайте UUID без `in-` вторым параметром. После 23 часов либо на паузе после истечения задания команда ставит найденный счёт на проверку через GET. Обработчик сверяет счёт и подтверждённую оплату, а затем обновляет исходную попытку.

   ```sql
   select app_private.royalty_checkout_recover($1::uuid,$2::uuid);
   ```

2. Если счёт или платёж найти не удалось, уточните результат в ЮKassa по ShopID и ключу идемпотентности, равному UUID попытки. Если ЮKassa подтвердила, что счёт не создан и оплаты не было, владелец БД может снять блокировку после 24 часов с исходной отправки. Исправьте причину ошибки перед повторным запросом из кабинета. Передайте UUID попытки и ShopID.

   ```sql
   update app_private.royalty_checkout_attempt
   set status='canceled',lease=null,lease_until=null
   where id=$1::uuid and invoice_shop_id=$2::text and status='open'
     and provider_id is null and recovery_provider_id is null and checkout_url is null
     and first_dispatch_at<=now()-interval '24 hours'
     and (lease_until is null or lease_until<=now());
   ```
