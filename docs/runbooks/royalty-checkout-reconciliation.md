# Сверка тестовой оплаты после потери ответа ЮKassa

Порядок применяется только в изолированной базе `bron_royalty_test` и тестовом магазине ЮKassa. Если ответ на создание платежа потерялся, процесс повторяет запрос с ключом исходной попытки в течение 23 часов при сохранении прежних условий оплаты. Затем попытка остаётся на проверке. Новая попытка за этот месяц может привести к повторной оплате.

1. Владелец тестовой БД находит незавершённую попытку в `app_private.royalty_checkout_attempt` по тестовому франчайзи и месяцу. Для сверки нужны UUID попытки, расчётный месяц и сумма в копейках.
2. В тестовом магазине найдите исходный платёж по сумме и периоду. Сверьте UUID попытки с `metadata.royalty_attempt_id`, если метаданные доступны. Скопируйте UUID платежа ЮKassa. Если подходящий платёж не найден, оставьте попытку на проверке до выяснения результата в тестовом магазине.
3. Через закрытое подключение к тестовой БД владелец выполняет команду с двумя параметрами. Первый параметр — UUID попытки, второй — UUID платежа из магазина.

   ```sql
   select app_private.royalty_checkout_recover($1::uuid, $2::uuid);
   ```

   Результат `true` ставит найденный идентификатор в очередь на сверку. При `false` проверьте, что с первой отправки прошло 23 часа, срок текущего задания истёк, попытка открыта и подтверждённый идентификатор ещё отсутствует. Доступа приложения и обычных прав процесса для этой операции недостаточно.
4. Запустите штатный тестовый процесс `node scripts/royalty-yookassa.mjs`. Для предложенного UUID он выполняет GET в API магазина и сверяет идентификатор, магазин, тестовый режим, валюту, исходную сумму и метаданные. Успех учитывается в исходном месяце один раз. Подтверждённая отмена снимает блокировку месяца. Платёж в ожидании остаётся в очереди на опрос.
5. Если UUID ошибочен, проверки оставят попытку открытой. После окончания задания исправьте UUID той же закрытой командой. Записи со статусом `succeeded` защищены от удаления через журнал ручных оплат.
