# T63 — утренняя работа сотрудников

## Договор исполнения

Новый ограниченный task активирует исполнителя после закрытия прежней роли.
Production остаётся публичным во время исполнения, ожидания владельца и после
закрытия роли. Source INACTIVE; любые Source SQL/POST/restore/reader запрещены.
Старые migration ledgers/guards T01–T62 не менять. Текущий релиз уже принят:
настоящая заявка с лендинга и создание франчайзи сработали.

Основание — последние уточнения владельца: дневная зарплата по выручке,
исправление сотрудником 5 минут, автономные доступы/управляющие, этапы карточек,
его таблица ноябрьской выручки и личный TXT входов. Новые общие пароли, reset
старых аккаунтов, удаление записей и выдумывание прошлых смен не разрешены.

Пакет: `docs/runbooks/payloads/t63-morning-update.json`. Точные task commit и SHA
manifest сообщаются в EXECUTOR_TASK. Все объявленные файлы сверить с этим commit.
ACCEPTED отправить со state path и сразу продолжить; ответ Root не требуется.
Локальный state `/private/tmp/bron-release-executor-20261113/T63-state.json` 0600;
серверный каталог `/root/bron-secrets/t63-morning` 0700. В state разделять шаги
NOT_RUN/PASS/BLOCKED и фактические записи, не заменять отсутствие результата PASS.

## 3. Атомарно применить только три новые миграции

```sh
python3 -I /root/bron-secrets/t63-morning/morning-target-operator.py --migrate --directory /root/bron-secrets/t63-morning --manifest /root/bron-secrets/t63-morning/migration-manifest.json
```

Ожидается MIGRATIONS_COMMITTED. Helper проверяет действующую свежесть уже
созданной копии/health, не создаёт backup и не повторяет restore. Три SQL и их
checksum ledger применяются одной транзакцией; старые миграции не запускаются.
SQL-ошибка до COMMIT откатывает изменения. При обрыве/intent без receipt один
read-only ledger check по этим трём именам определяет COMMITTED/NOT_COMMITTED/
UNKNOWN; не повторять вслепую. В чат только фиксированный код/SQLSTATE, не stderr.

Миграции сохраняют старые RPC и закрытые смены; новая RUB-сетка — default при
отсутствии явной политики франчайзи. TRY/KZT и свои сохранённые сетки не менять.
Стандарт — max(минимум, процент)+премия; отдельный фикс — фикс+процент. История
не пересчитывается. Управляющий ограничен назначенными точками; франчайзи
сохраняет управление всей своей компанией. История блокировки не возвращает
снятую роль управляющего.

## 4. Опубликовать готовый клиент без перезапуска

Только после MIGRATIONS_COMMITTED:

```sh
python3 -I /root/bron-secrets/t63-morning/morning-static-publish.py --publish --directory /root/bron-secrets/t63-morning --archive /root/bron-secrets/t63-morning/app-root.tar --pin /root/bron-secrets/t63-morning/publish-pin.json
```

Ожидается APP_PUBLISHED. Проверяются все файлы архива, manifest, root PWA scope,
три ledger checksum, существующий production parent bind и шесть backend IDs.
Меняется только app-каталог атомарным Linux exchange. Старые hashed assets
сохраняются для открытых вкладок/PWA; before-image остаётся на сервере.
Никакого service restart, режима maintenance или изменения landing/status.

Один bounded strict-TLS GET каждого app `/`, `/app-version.json`,
`/manifest.webmanifest`, `/sw.js`: HTTP200; версия/manifest соответствуют архиву.
GET landing HTTP200 и существующего backup health HTTP200/healthy/fresh.
Один `ping` через обычную авторизованную сессию приложения (или прежний T62
VPS-способ с public anon key) — `ok`, без business rows. Не печатать ключ/headers.
Не повторять старые Auth/RLS/restore/Telegram/migration сравнения.

При подтверждённом критическом сбое нового клиента вернуть прежний **публичный**
клиент одной командой и проверить его HTTP200:

```sh
python3 -I /root/bron-secrets/t63-morning/morning-static-publish.py --rollback --directory /root/bron-secrets/t63-morning
```

Обратно совместимую схему и реальные записи не удалять. При UNKNOWN сначала
сверить существующие result/manifest, не повторять publish/rollback. Source
в любом случае INACTIVE; активность роли не является причиной maintenance.

## 5. Внести только подтверждённую ноябрьскую выручку

Работать в существующей законной сессии приложения: «Франчайзи» → однозначно
найденный партнёр/единственная точка владельца таблицы → ноябрь2026, RUB.
Значения брать **только из фото/сообщения владельца**, не из примера/seed.
Это 14 заполненных дней 02–15, контрольная сумма 79 400 RUB.

Полный порядок [здесь](payloads/morning-revenue-import.md): до первой записи
сверить все предоставленные дни. Совпадения пропустить; любой уже существующий
отличающийся итог — CONFLICT, не перезаписывать. Отсутствующие дни внести обычным
полем «Вся выручка точки за день», без выдуманной cash/card разбивки. Не создавать
исторические смены/зарплату; пустые даты оставить «не внесено».

Не извлекать/переносить JWT и не создавать фиктивный actor/session ради SQL.
При отсутствии действующей сессии записать OWNER_SESSION_REQUIRED и продолжить
остальную независимую приёмку. Если UI сохраняет в offline queue, остановить
новые записи: очередь не равна COMMITTED. Итог — числа saved/matching/conflict/
pending и подтверждённая сверка 14 предоставленных дней; не выдавать частичный
импорт за полный. Не запускать `npm run import:sheets`.

## 6. Реальные доступы и приёмка

По закрытой инвентаризации и обычному UI проверить запрошенных владельцем
стажёра и управляющего. Нельзя утверждать «500 ₽ настроено» лишь по коду:
проверить employee_kind, текущие даты/минимум и фактическую политику. Не менять
даты стажировки на выдуманные, не пересчитывать старые смены. Существующее
явное назначение управляющего сохранить. Если legacy manager без staff-point
назначения, франчайзи/сетевой менеджер может назначить через новый «Точки и роль»
только его однозначно подтверждённую точку; несколько точек не выбирать наугад.
Смена назначения завершает его старые сессии — это ожидаемо, пароль не меняется.

Ничего не создавать ради теста: реальные входы/операции — только по настоящей
работе сотрудников. Существующая сессия менеджера: сохранённый этап карточки,
сотрудники/назначения, экономика→роялти. Для сотрудника при законном действующем
входе: свои точки, открытие настоящей сегодняшней смены при выходе на работу,
история месяцев, расчёт предварительной зарплаты. Не закрывать смену фиктивной
выручкой ради теста. Для управляющего: только свои точки/выручка, заказы.
На телефоне/PWA обновить штатно; не очищать storage/очередь и не разлогинивать
владельца ради проверки. Если реальный вход ещё не выполнен, это PENDING.

## Завершение и отчёт

Без лишних новых согласований продолжать разрешённую последовательность после
каждого PASS. При BLOCKED остановить зависимую мутацию, продолжить независимые
ветки. Новая парольная запись/неизвестные условия денег требуют отдельного
точного решения владельца; не тормозят публикацию проверенного клиента.

Одна каноническая квитанция `/root/bron-secrets/t63-release-receipt.json` 0600 и
идентичный безопасный local mirror: task/commit/manifest SHA, inventory counts,
migration status/3checksums, archive+live manifest SHA, backend invariants,
static/API checks, revenue saved/matching/conflict/pending counts, role/pay
verified versus blocked, TXT path, real-user acceptance versus pending,
changed paths, sourceQueries=0, passwordsReset=0, servingMode=PRODUCTION_PUBLIC.
Без имён/логинов/UUID/денег по дням/паролей в чате и публичных артефактах.

В каждом обновлении одна строка: принято/подтверждено → текущий блокер → следующий
шаг и ориентир времени. Финальный статус UPDATE_LIVE_ACCEPTED, UPDATE_LIVE_WITH_
PENDING_INPUTS либо BLOCKED_без_публикации; роль активна до явного закрытия,
production остаётся публичным.

Отложено: общая касса нескольких сотрудников, дневной минимум при двух точках,
месячный оклад/пропорциональность, email-инвайты, произвольный RBAC, бухгалтерия,
новые интеграции и косметическая оптимизация. Открытые решения —
[backlog](../product-backlog.md).
