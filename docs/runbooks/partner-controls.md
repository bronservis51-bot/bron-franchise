# Выпуск упрощённого кабинета

1. Закрытая копия бизнес-таблиц, восстановление в изолированной БД, сверка строк,
   UUID и сумм по валютам. Не запускать seed/reset на рабочей базе.
2. Применить `20261108211104_partner_controls.sql` и записать SHA256 файла в
   `app_private.schema_migration`. Ранее применённые файлы не менять.
3. Сверить старые поля всех таблиц; допустимы новые справочные права и роль.
   Переименование конкретного владельца выполняется отдельной адресной операцией
   с проверкой UUID и прежнего имени; внутренние идентификаторы не меняются.
4. Приостановить только cron `bron-shop-worker`; `bron-jobs` продолжает работать.
   `procurement_shop_settings.enabled` остаётся false. Для возврата обработчика
   есть installer в runbook shop-automation; включать без токена и пилота нельзя.
5. Опубликовать проверенную сборку. Проверить обновление старой PWA без потери
   сессии, очереди и ввода. Открыть «Заказ / Предзаказ», вопрос по статье, выручку.
6. Владелец → Сотрудники → Управляющие → Добавить. Передать выданный пароль
   лично; не сохранять его в репозитории. Управляющий добавляет только продавцов
   своего партнёра. Закрыть/вернуть доступ — без удаления смен.
7. Для параллельного входа открыть обычную ссылку и `?profile=manager#/login`.
   Параметр изолирует локальную сессию, не меняет серверную роль.

## Проверки и ограничения

Автотесты: область доступа, создание/повтор/отзыв/восстановление, сохранение
открытой смены, выручка владельца + смены, повтор/конфликт/офлайн, роялти 7%,
остаток после расходов, февраль/март, нулевой день недели в прогнозе, контракт
анонимной формы лендинга. Синтетические браузерные проверки 320–1920 px и
200% текста не заменяют реальный iPhone с клавиатурой.

Создание Auth-пользователей использует существующую серверную функцию проекта;
локальная проверка не доказывает работу внешнего сервиса входа. Первый реальный
управляющий требует обычного входа и проверки на его устройстве. Не создавать
фиктивных пользователей или заявок в production для тестирования.

Откат интерфейса не требует удаления таблиц/ролей/записей. После появления
деклараций выручки нельзя откатывать модель данных к cash+card: потеряется часть
выручки без разбивки. Исправлять новой миграцией.
