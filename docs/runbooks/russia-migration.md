# Перенос в РФ: исполнение и допуск

Проверено 10.11.2026. Статус: подготовка; сервер не заказан, полное восстановление
и переключение не выполнялись. Рабочая система остаётся на прежней площадке.
Выполнять следующий этап только на изолированном сервере в РФ.

Дополнительные обязательные условия: [критерии релиза](../release-gates.md) и
[ADR-0021](../adr/0021-release-ownership-and-final-cutover.md). Бессрочный зарубежный
приём новых анкет после локализации не допускается; мост используется для сверки
переходных записей с проверенным окончанием старой записи.

## Площадка и расходы до оплаты

Предложен AdminVPS **Start (Россия)**: 4 CPU / 8 GB / 80 GB NVMe,
Ubuntu 24.04, без панели и приложений маркетплейса. В форме заказа подтверждены
1 289 ₽/мес. с НДС, установка 0 ₽ и одна еженедельная копия без доплаты.
Основной IPv4 входит в тариф; дополнительные адреса не нужны.
При повторной проверке формы поддержки 10.11.2026 указана активация российских
серверов до двух дней. В форме также есть предупреждение об ответах по тикетам
до пяти дней из-за нагрузки по европейским серверам; применимость к авариям
российского VPS и фактический срок реакции нужно получить письменно до оплаты.
Это предложение к оплате, не действующий сервер и не обещание срока миграции.

Второй провайдер для закрытых зашифрованных копий — Timeweb Cloud S3,
Санкт-Петербург, стандартное хранилище 10 GB: 79 ₽/мес. Форма должна показывать
**«Приватный»**. Внешний трафик сверх включённого лимита, увеличение объёма и
переход на следующий тариф оплачиваются отдельно; следить за заполнением.

Продление доменов не равно цене регистрации: .ru «Стандарт» сейчас 399 ₽/год;

в Cloud проверяется перед продлением. Отдельный подрядчик для администрирования
не заказан и в эти суммы не включён. Поддержка VPS не является сопровождением
Supabase. Назначить ответственного за обновления, тревоги и восстановление;
согласовать стоимость его работы, если это внешний специалист.

Проверка наличия важнее поискового сниппета: дешёвые Selectel VDS распроданы;
Beget временно не принимает новые VPS; часть московских Timeweb — предзаказ.
Не покупать альтернативу автоматически при изменении цены или доступности.

## Что нужно извне

- Оплата и личный аккаунт владельца у выбранного провайдера. Реквизиты плательщика
  и принятие договора выполняет владелец. Заказ не отправлять до согласования.
- Администратор доменов Timeweb прошёл идентификацию через ЕСИА: статус
  «Данные подтверждены», выбран в обеих карточках корзины. Домены ещё не куплены.
  Не копировать паспортные данные в репозиторий или отчёты. Корзина повторно
  включила платные SSL/WHOIS при открытии: их отключили, итог 400 ₽ за первый год.
  Перед оплатой снова сверить итог и отсутствие платных дополнений.
- Действующий прямой пароль PostgreSQL исходного Supabase. MCP SQL и публичный
  ключ клиента не дают `pg_dump`-подключения. Пароли пользователей не менять.
  Секрет вводится в закрытое окружение администратора на сервере в РФ, не в git.

## До первого изменения источника

1. Зафиксировать HEAD обоих репозиториев, состояние источника, версии Postgres,
   Auth и Storage, расширения, Auth settings, закрытую регистрацию, JWT/signing
   settings, SMTP, Edge Functions, задания cron, Vault и серверные секреты.
   Секреты не печатать в журналах. На 10.11 источник — PostgreSQL 17.11;
   upstream self-hosted/v0.8.4 всё ещё содержит Postgres 17.6.1.136: этот образ
   не считать автоматически допущенным в production. Проверить исправленный
   совместимый образ по официальным релизам и репетиции.
2. Сохранить полную исходную копию roles/schema/data официальным Supabase CLI
   после проверки `--help` установленной версии. Выполнять выгрузку на сервере
   в РФ. Auth, identities, password hashes, app_private и ключи повторов обязательны.
   Хранить зашифрованно вне git и вне единственного VPS. JSON не заменяет SQL-копию.
3. Объекты Storage копируются отдельно, включая не прикреплённые к документам.
   Зафиксировать список, размер и SHA-256 каждого файла; проверить владельцев,
   бакеты, политики, grants и закрытые временные ссылки. Пустое хранилище тоже
   проверяется заново в финальном окне, поскольку до него могут загрузить файл.
4. Vault требует отдельного переноса секретов/ключей шифрования. Перенос только
   зашифрованных строк без проверенного чтения на цели недостаточен. У источника
   есть cron `bron-jobs` (активен каждые 5 минут), `bron-shop-worker` (выключен),
   и Edge Function `shop-worker`. Сохранить состояние «выключен», не запускать
   интеграцию закупок автоматически; облачный URL в cron заменить на целевой
   только после проверки серверных секретов и авторизации.
5. Использовать [конфигурацию HTTPS и Docker](../../deploy/timeweb/README.md)
   как переносимый каркас; она подходит и для обычного VPS другого провайдера.
   БД/pooler/Studio закрыты снаружи, SSH ограничен, оба сайта и API в РФ.
   До DNS-переключения цель доступна только администратору для репетиции.

## Репетиция и финальное окно

- Восстановить свежую полную копию на отдельной цели по официальной процедуре.
  Сначала `npm run migration:check`, затем пробные входы: они меняют Auth-метаданные.
  Сверка теперь включает Storage metadata/policies/grants, прикладные триггеры,
  колонковые права и версии расширений. Различия версий/владельцев разобрать явно;
  не заменять строгую сверку сравнением одних количеств.
- Проверить обычный вход директора, владельца и сотрудника с прежним паролем;
  чужого партнёра, анонима и отозванную сессию; смены, выручку, роялти по валютам,
  документы и идемпотентность. Запись проверять только на изолированной копии.
- До открытия цели отозвать на **цели** перенесённые sessions/refresh tokens;
  новые JWT secrets сами по себе не отзывают refresh tokens. UUID/пароли сохраняются.
- Развернуть [мост поздних заявок](late-leads.md). Старая форма продолжает работать;
  до окончательного переключения исходные UUID сохраняются, правки менеджера на
  цели не перезаписываются. После запуска российского приёмника старую зарубежную
  запись прекратить по ADR-0021; старые загруженные формы учесть отдельно.
- Перед финальной копией завершить очередь источника, остановить новые денежные
  записи, перенести изменения и повторить сверку. Старый origin/PWA обновляется
  на целевой backend и остаётся доступным для отправки оставшейся origin-очереди.
  Безусловный redirect до обработки очереди запрещён.
- Только затем новые сборки обоих сайтов, HTTPS/DNS, проверка установленной старой
  PWA и новой установки, реального входа/заявок с нужных сетей. После первых записей
  на цели откат требует обратной сверки, одного возврата DNS недостаточно.

## Резервирование и наблюдение

Настроить часовые зашифрованные копии БД/Auth/конфигурации и согласованные копии
файлов в независимый приватный S3 в РФ. Согласованность файлов и metadata должна
быть проверена, включая загрузку/удаление во время копирования. Хранить 24 часовых,
30 дневных и 12 месячных точек, контролируя фактический объём. Перед переключением
восстановить одну копию из S3 на чистой цели и измерить время. Цели RPO ≤ 1 ч,
RTO ≤ 4 ч не объявляются достигнутыми до измерения.

Проверять frontend version, Auth health, ping и контракт `lead_submit` каждые
5 минут, без создания фиктивной заявки; диск/память/состояние контейнеров и возраст
успешной копии — отдельно. Выбрать реальный канал тревог и ответственного до запуска.
Наличие скрипта или cron в git не доказывает действующее расписание/оповещение.

После переключения задать `APP_URL=https://bsfranchise.site/` и новые публичные
`VITE_SUPABASE_*` в окружении `scripts/check-availability.mjs` и GitHub Variables.
Старое значение по умолчанию сохранено для текущего GitHub Pages до переключения.
Публичные синтетические проверки можно выполнять извне, персональные данные и
резервные копии в GitHub Actions не передавать.

Источник выводится из эксплуатации только после сверки новых записей, поздних
заявок и старых очередей. Удаление исходных данных и снятие услуг фиксируются
отдельно; наличие новой страницы или сертификата не завершает перенос.
