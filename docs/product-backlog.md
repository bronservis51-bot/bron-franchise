[Приложение](https://app.bronservis.ru/) и [лендинг](https://bronservis.ru/)
публичны. Владелец проверил настоящую заявку с лендинга и создание франчайзи.
Source INACTIVE. По отчёту исполнителя T63: три закреплённые миграции применены,
клиент опубликован атомарно; strict TLS/live checks/ping, backup health PASS.
Все 14 предоставленных дней ноябрьской выручки сверены без конфликтов;
пустые дни не изменены. Частные имена, UUID и суммы по дням не публикуются здесь.

Уже выпущено; заново разрабатывать не нужно:

- Дневные RUB-ступени по фото, месячная сумма и история заработка.
- Стандарт `max(минимум, процент) + премия`; существующий отдельный режим
  `фикс за смену + процент`. **Месячный оклад не реализован.**
- Снимок условий смены: открытая/закрытая смена удерживает прежние условия.
  Запланированное применение новой версии с будущей даты пока не реализовано.
- Пять минут на свою поправку выручки по серверному времени от первой сдачи,
  аудит до/после, контроль revision и повтора; поправка не продлевает окно.
- Основные самостоятельные доступы франчайзи: создание, блокировка,
  восстановление, смена пароля, управляющий, несколько точек/ротации, отзыв сессий
  и история доступа. Управляющий видит разрешённые точки и заказы.
- Независимые этапы подготовки франчайзи, компактный вход, роялти внутри Экономики.

По последующим отчётам T64 миграции и клиент установлены. Прежний отказ списка
сотрудников устранён: франчайзи видит команду, сотрудник входит и видит личный
расчёт/историю. Для запрошенного стажёра сохранены подтверждённые даты 1–30 ноября,
личный минимум 500 RUB и ступенчатая схема; закрытая смена, второй сотрудник
и общая политика не изменились. Владелец подтвердил работу PWA на своём телефоне;
это не подтверждает отдельное устройство сотрудника.

**PENDING реальной приёмки:** настоящий новый цикл смены при выходе сотрудника
на работу; прямой live RPC-контроль отказа рейтинга для франчайзи. Серверные
изолированные тесты, применение миграции, UI-рейтинг менеджера и перенаправление
франчайзи проверены, но не подменяют незапущенный RPC. Исполнение T63/T64 можно
закрыть с этими явно открытыми пунктами, без заявления полной live-приёмки.
См. [решение о завершении исполнения](runbooks/t63-t64-closeout-20261116.md).

## Порядок небольших отдельно принимаемых выпусков

### Срочное обновление T64 — установлено, остаток приёмки записан

Прямое уточнение владельца 16.11: завершить рабочие сценарии, не ограничиваться
планом. Подтверждённый пользователем отказ «Недостаточно прав» у франчайзи и
сотрудников — P0. Проверить и исправить причину без произвольной выдачи ролей.

- Рейтинг разрешён только менеджеру по франшизе: меню, прямой маршрут и серверные
  данные. Франчайзи/управляющий/сотрудник рейтинг не видят.
- Менеджер по франшизе может задавать и изменять телефон-логин. Для новых
  прикладных аккаунтов логин — номер телефона; старые логины меняются явно,
  только на подтверждённый номер, без массовой переименовки по догадке.
  UUID, пароль, права и история сохраняются; смена логина отзывает старые сессии.
- Продолжить приёмку настоящих сотрудников и телефона/PWA после исправления
  доступа. Не подставлять тестовую выручку ради зелёной проверки.

По отчётам исполнителя установка T64 завершена, canonical receipt и private
mirror совпадают. Код, применение и пользовательская приёмка учитываются
раздельно. Смена реального телефона не проводилась ради теста; изолированные
проверки и наличие интерфейса не обозначают выполненную production-мутацию.

### Отдельная следующая задача — три реальных сотрудника

Владелец запросил три профиля существующего франчайзи по подтверждённым точкам.
Список/сопоставление уже проверены в авторизованной форме; повторять их ради
ожидания ввода не требуется. Персональные данные в публичный backlog не включать.
Новые профили не являются условием закрытия исполнительской роли T63/T64.

Нужен один закрытый ввод: реальный телефон каждого (новый login), обычный
сотрудник/стажёр и точный вариант оплаты. Для общей ступенчатой схемы отдельный
процент не нужен; для фикс+процент нужны согласованные фикс за смену и единая
ставка; для стажёра — подтверждённые даты. Никаких вымышленных телефонов,
автоматического назначения стажировки или сохранения оплаты по догадке.
Владелец вводит телефоны в существующей форме приложения либо передаёт их через
уже разрешённый закрытый канал. В чат/репозиторий телефоны и пароли не включать.
Текущий файл выдачи содержит лишь логины; возможность собрать все старые пароли
не подтверждена и не разрешает их сбросить. Новые реквизиты выдаются лично.
Черновик T65 с разрешением коротких логинов отменён после поправки владельца;
он не опубликован, phone-only для новых сотрудников сохранён.

### Следующие отдельно проверяемые выпуски
Подробный [план после публичного запуска](post-release-plan.md) задаёт минимальный
безопасный объём и независимые сценарии приёмки по новым требованиям владельца.
Порядок доработок: автономность и защита владельца → достоверность смен
→ версии/два режима оплаты → экономика. Приёмка короткого входа независима.
Это не переоткрывает запуск; уже опубликованное повторно не разрабатывать.

| --- | --- | --- | --- |
| **P0 — завершение пилота** | Разобрать конкретный отказ разрешённого списка, настоящий вход/смена, телефон/PWA | Своя область доступна, чужая отклонена сервером. Реальная рабочая операция проходит без фиктивной выручки. История, ввод и очередь сохраняются | Реальное назначение/вход. Исправлять только подтверждённый дефект; остальной backlog пилот не блокирует |
| **P1.1 — полный цикл команды** | Довести уже существующие создание, точки/роль, деактивацию, восстановление и аудит | Франчайзи проходит цикл без менеджера сети. Нет самоповышения/чужих точек. Снятая роль не возвращается после блокировки. Старые сессии отозваны, смены и зарплата сохранены; секретов в аудите нет | Сначала приёмка текущего T63; переписывать работающие функции не нужно |
| **P1.2 — исключения смен** | Довести обзор пропусков/незакрытых смен, поправок и спорных состояний | Пропуск, открытая смена и подтверждённый ноль различимы. Нет авто-нуля/авто-закрытия. Открытая смена держит снимок, история не пересчитывается. Конкурентная правка даёт явный конфликт | Один существующий серверный расчёт и снимки, без параллельного движка зарплаты |
| **P1.4 — отдельный оклад + процент** | Реализовать только согласованный период/правила оклада | Старый max(минимум, процент)+премия неизменен. Новый режим выбирается явно. Процент считается ежедневно от кассы; месячный оклад, если выбран, не начисляется целиком за каждую смену. Версии и снимки сохраняются | Решение PAY-02; текущий фикс за смену + процент уже есть |

повторов и конфликта, если затрагивает эти контракты. Число тестов не заменяет
реальную приёмку. Изменения небольшие и добавочные на существующем стеке.

## Решения владельца до реализации соответствующего правила

Их не нужно запрашивать сейчас для продолжения пилота.

| ID | Вопрос | До решения |
| --- | --- | --- |
| PAY-01 | Несколько сотрудников за одной кассой: личная/общая база, доля процента/премии, пересечение смен | Не делить автоматически и не начислять каждому процент от одной общей кассы. Сохранять отдельные отчёты, не обещать утверждённого совместного расчёта |
| PAY-02 | Оклад месячный или за смену? Для месячного: неполный месяц, пропуски/ротации, распределение, премия | Сохранить существующий фикс за смену + процент. Месячные формулы не включать без решения |
| PAY-03 | Один человек на двух точках за день: минимум каждой смены или общий дневной? | Сохранить действующий минимум за смену, не придумывать дневной cap/распределение |
| ACCESS-01 | Канал приглашений и безопасного самостоятельного восстановления | Существующие создание/сброс франчайзи и личная смена пароля; не обещать email на служебный адрес |

Подтверждённая RUB-сетка: пороги 0/8/10/13/16/19/23 тыс.,
16/17/18/19/19/20/21%, премии 0/0/0/0/200/200/300 RUB. Нижняя граница включена;
процент от всей кассы смены, не прогрессивно и не от месячной суммы. Действующий
обычный минимум 1000 RUB сохранён; стажёрский 500 RUB проверяется по фактическим
условиям. Явные политики и другие валюты не переписываются новой default-сеткой.
Начислено не означает выплачено.

## Закрытый файл реквизитов доступа

Только owner-only TXT: не git/issue/build/технический лог/общий чат. Включать
только действующие прикладные логины; пароль — только уже имеющийся из законно
выданного закрытого листка, сопоставленный по точному логину, не по имени.
Отсутствующий пароль явно пометить отсутствующим. Хеш не является паролем и не
экспортируется. Наличие старого выданного листка не доказывает успешный вход.
Текущий файл T63 содержит только логины; новую сводку создавать отдельно,
сохранив оригинал и его SHA, и передавать лично владельцу.

Без отдельного точного разрешения нет reset/активации/смены ролей ради выгрузки.
Не читать личную историю/Passwords/DMG. Реквизиты VPS/S3/AGE/БД/Telegram сюда не
входят. Путь к заранее выданному закрытому листку не означает разрешения сканировать
все личные файлы. Если листка нет, это ограничение файла, а не повод сбрасывать пароль.

## Неприкосновенные границы

- Один серверный контракт расчёта/прав, добавочные миграции; без нового
  универсального конструктора ролей/зарплаты и обязательных сервисов.
- Различать менеджера сети и управляющего точки. Несколько точек и ротации
  поддерживать без жёсткого графика и обязательной линейной последовательности.
- Нет повторного Source-переноса/снимков, seed/reset базы, выдуманных смен/нулей,
  удаления очереди PWA и молчаливого перерасчёта прошлого.
- Проверять затронутую часть. Backup/restore/Telegram не повторять без
  соответствующего изменения или сбоя.
- Наличие кода, применение SQL, публикация и подтверждённая работа пользователя —
  разные состояния. Доступ координатора к Chrome/SSH не является release gate.
- Новая автоматизация, косметика и интеграции не задерживают публичный пилот.
