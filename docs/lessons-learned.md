## 14.11.2026 — повтор compact-запроса не заменяет проверку передачи

- T36 закрыл actualHTTPS→DB synthetic gate; не повторять транспортные пробы.
  Full audit + compactAuth должны разделять ОДИН RR snapshot: отдельный capture
  после COMMIT допускает drift. Optional beforeCommit и native concurrent-update
  fixture проверяют эту границу до выдачи пакета.
- Документация platform invocations допускает body logging; нулевой observed
  count не доказывает universal retention. Реальный private payload шифровать
  до HTTP и расшифровывать только VPSRAM; HKDF input — secret, не public capSHA.
- Auto-review отклонил T37 deploy по sensitive payload/source→VPS authorization.
  Не обходить исполнителем или другим endpoint. Подготовить проверяемый scope/код
  и запросить только нужное явное разрешение; prepared не называть issued/deployed.

- T35 settings200/610bytes доказал HTTPS >512; REST401 — отдельный отказ доступа,
  не продолжение TCP-timeout и не основание менять grants. Сохранять общий
  BLOCKED и полезный partial proof одновременно. Следующий probe использует
  обязательный private capability, а не публичный anon JWT как секрет.
- Ready/deploy handoff должен быть частью одного пакета: READY с hash/expiry
  отправляется сразу, bounded readiness WAIT допускает одно явное продолжение
  без новой capability/нового task ID и без расхода actual one-run guard.
  Повтор реального probe после FAIL этим не разрешается.
- Negative TLS proof не принимает generic TLS reset/timeout за certificate
  identity rejection. Protocol marker и response schema клиента/Edge сверять
  до выдачи пакета, чтобы техническая несовместимость не съела единственный run.

- T34 независимый libpq тоже не получил FIRST512 при успешных TLS/identity/RO.
  Перебирать тот же TCP подход дальше без нового основания неэффективно. HTTPS
  существующей платформы — другой путь; metadata probe не называть уже миграцией.
- Hosted Edge Node TLS API имеет отличия: checkServerIdentity/getPeerCertificate
  могут быть stub. Проверять фактическую identity negative, а не эти флаги; pg
  перезаписывает servername для FQDN host, поэтому negative должен использовать
  один resolvedIP и явно другойSNI. Общий nativeNode proof не покрывает hostedEdge.
- Private endpoint требует абсолютного expiry, фиксированных операций/READONLY,
  secret толькоVPS и actuallog-leak проверки до userdata. Не подменять безопасность
  публичным anonJWT и не создавать произвольный SQL-over-HTTP API.
- T33 дал тот же128PASS/512timeout на двух других canonical peers. Не делать ещё
  один такой Node probe: независимый клиент и порядок ответов снимают другую
  неизвестность. Libpq PASS сам по себе не доказывает конкретный дефект Node или
  провайдера; его безопасные partial counts сохранять даже при позднем отказе.
- Native TLS/client тест не должен читать password из image defaults. Key-only
  unsets при чистом Docker CLI env + strict service/pgpass подтверждены реальным
  SCRAM и poisoned-env negative cases, без credential values вargv/env/log.
- Проверять future freeze draft на реальных READONLY metadata до one-shot task:
  отличавшийся literal 'cron' выявлен и исправлен до source effects; активный job
  не меняли/не восстанавливали удалённый run_jobs. Отсутствие прямых унаследованных
  write grants у lookup-role не исключает NOINHERIT SET ROLE — проверять и этот путь.
- T32 реально изменил TCP MSS, но512bytes снова не пришли; точный inverse выполнен.
  Не повторять эту гипотезу без новых данных. CanonicalDNS имеет несколько peer:
  отрицательный результат на одном не переносится на остальные; разрешённый bounded
  перебор других адресов сохраняет тот же host/CA/SNI и не меняет network settings.
- Native PG через plaintext PgPipe не проверяет TLS stack. Добавлен actualTLS
  proof на точном Node22.23.5/pg8.23.1/PG17.12, включая размеры и неверные CA/name.
  PASS локального TLS не доказывает сеть VPS/поведение реального pooler.
- T31: TLS/identity/128bytes PASS,512bytes timeout, unacked1/RTO6656. Предварительное
  условие512PASS остановило ещё НЕ исполнявшийся host-only эксперимент; это граница
  пакета, а не доказанная невозможность проверить маршрут. T32 использует exact
  уже полученный128PASS/512timeout, не повторяет baseline и сохраняет все final gates.
- GitHub DNS отказ на Mac не означает отсутствующий commit. Одно подтверждённое
  per-command curloptResolve с sslVerify=true восстановило fetch; не менять hosts,
  не отключать TLS и не заменять проверку manifest предположением о публикации.
- T29 raw Auth и T30 compact Auth оба завершились client timeout. Source backend
  T30 уже был idle/ClientRead после SELECT: медленный SQL этим не доказан.
  Следующий шаг — разные размеры и multi-row СИНТЕТИЧЕСКОГО ответа на одном peer,
  а не ещё одна вариация Auth SELECT или повтор всей инвентаризации.
- В сравнении маршрутов фиксировать один canonical DNS IP и прежние CA/SNI.
  MSS/MTU — лишь проверяемая гипотеза. Разрешённый локальный эксперимент имеет
  точный host-only before-image/inverse, не затрагивает default route/firewall

- Закрытый frontend не гарантирует cleanup backend в pooler. Для probes применять
  local idle-in-transaction timeout, учитывать собственный server session отдельно.
  ExclusiveLock на virtualxid штатен даже при READ ONLY; перед выводом о записи
  проверять locktype, relation modes и XID, не завершать чужие/неизвестные сеансы.
- Настоящий schedule43533210497 на T22 merge прошёл без нового dispatch/cron fix.
  Переиспользовать этот факт; неизвестную причину задержки не выдавать за диагноз.

## 14.11.2026 — опубликованная инструкция не подтверждает старт

- Координатор поставил T27 в зависимость от T26, хотя ACCEPTED/RUNNING T26 не было.
  Исполнитель сообщил об отсутствии T26 receipt/process на VPS и локального receipt;
  очередь заблокировалась на неподтверждённом старте. Это ошибка передачи координатора.
- Различать ISSUED/ACCEPTED/RUNNING/CLOSED. Исполнитель отправляет ACCEPTED сразу
  после записи состояния и продолжает без нового разрешения. Не вводить второй ACK.
- Если доказательств исполнения нет, не придумывать completed receipt. Новый T28
  объединяет неисполненные действия после сверки, сохраняя cross-task guards.
  Один source restart и один inventory не становятся двумя из-за нового task ID.
- Exact canonical receipt path задавать заранее. BLOCKED по одной ветке не должен
  удерживать независимые owner/ticket/schedule ветки или итоговый отчёт.

## 14.11.2026 — почему день не завершился релизом и как не повторить

- Основные предотвратимые потери — дефекты сценариев координатора и организация
  handoff, а не недостаток старания владельца или самовольные остановки исполнителя.
  Серия restore T12–T21 исправляла bootstrap/порядок импорта, builtin plpgsql и
  сравнение sequence ACL; часть отказов не была повреждением рабочих данных.
- Сетевую проходимость и большой ответ следовало проверить до длинной подготовки.
  T24: client deadline60s на daily_revenue; T25: три общих10s route probes FAIL,
  стадия неизвестна. Это НЕ доказывает отказ TLS/неверный пароль/медленный PostgreSQL.
  Точная projection2975реальныхстрок выполнилась на source под server8s; полный
  ответ~3.8MB. T26 исправляет диагностику этапов и разрешает один управляемый ремонт.
- Psql JSON bridge скрыл несовместимость name[]/pg-драйвера; перед выдачей
  PG-sensitive пакета проверять фактические SQL, driver/types и нужное окружение.
  Не превращать успех одной модели теста в доказательство реального сервиса.
- Каждый мелкий пакет с инструкцией ждать создавал задержку координатора.
  Объединять действия до одного проверяемого результата, включать переходы после
  PASS и независимые ветки. Не расширять задним числом scope/one-run текущей задачи.
- Готовность компонентов не даёт достоверной оценки срока релиза. Сообщать
  критический блокер и наблюдаемые gates. Не сокращать срок ради желаемого ответа,
  не объявлять source/target финально равными по T12, пока source продолжает писать.
- Результаты T12/T14/T18/T19/T21 сохраняются; повтор требует указанного изменения
  или сбоя. Snapshot, новая backup freshness и личная приёмка имеют свои условия.
- Соблюдение Парето убирает доминируемые решения, лишние настройки и повторные
  проверки; не убирает data integrity, freeze, acceptance, security и safe rollback.

Техническое знание на случай доказанного bulk bottleneck: native PG17.12/pg8.23.1
на3002синтетическихстроках подтвердил builtin sha256 над конкатенацией
`UTF8-byte-length || ':' || full-row-text || LF` в C-order, как fingerprintRows.
Шесть сравнений, empty/duplicates/Unicode/control chars/bigint/decimal/microseconds
и mutation RED/GREEN PASS; сначала bounds в той же RR READ ONLY транзакции.
Это исследование, не установленный fast auditor. Применять только если T26 доказал
непригодную передачу; не hash-of-hashes, не исключение полей, не изменение T21 runtime.
Полный default/fast snapshot и PK-diff ещё требуют отдельной проверки до применения.

## 14.11.2026 — общий deadline не заменяет диагностику этапов сети

- T25 общий10s budget включал connect и пять roundtrips; FAIL нельзя приписывать
  bulk/TLS по одному итоговому коду. Ограничивать и измерять каждый этап отдельно,
  throughput — от начала передачи, без handshake. Проверять модель slow-connect.
- Listener/PID не доказывает работоспособный tunnel. При известной неисправности
  разрешать в одном пакете проверенный однократный restart выделенного wrapper
  и последующую приёмку, а не останавливать исполнителя после каждой инвентаризации.
- Пароль БД не переносить на Mac ради обхода сети. SSH -C не сжимает уже
  зашифрованный PG TLS; client-side pg_dump compression тоже не уменьшает PG wire.

## 13.11.2026 — client timeout не доказывает медленный PostgreSQL

- pg query_timeout ограничивает ожидание клиента, но не отменяет запрос сервера.
  Rollback за зависшим запросом может ждать ещё один такой интервал. Сохранить
  первый безопасный context и закрыть только собственный failed stream.
- PGOPTIONS через pooler не считать доказанным statement_timeout: устанавливать
  SET LOCAL внутри фактической read-only транзакции и проверять нативно.
- Сначала отделить серверную работу от передачи большого ответа: точная projection
  с агрегатом bytes/count на source, затем bounded known dummy bulk через VPS.
  Канонический прямой TLS6543 пригоден для одного readonly transaction snapshot,
  но не становится автоматически подходящим для session-bound freeze/control.

## 13.11.2026 — PostgreSQL native proof должен включать рабочий драйвер

- Psql→JSON bridge подтверждает SQL, но меняет типизацию ответа: name[] становится
  JSON-массивом, тогда как pg8.23.1 возвращает строку. Для PK metadata использовать
  явный text[] и проверять тип. Перед поручением проверять настоящий driver/wire/OID,
  а не называть одну SQL-проверку доказательством всего runtime.
- Одна метка DELTA_FAILED скрыла причину source-отказа. Сообщать fixed error code,
  безопасный operation/object/ordinal и elapsedMs; не печатать исходный message,
  detail/hint/stack/SQL. При rollback сохранять первое место отказа.
- Найденный поздний driver bug не доказывает причину более ранней ошибки. Хранить
  UNKNOWN до фактической диагностики; не повторять прежний one-run task.

## 13.11.2026 — начальная роль и чтение custom-архива PostgreSQL

- Не удалять исходный builtin `plpgsql` перед установкой остальных расширений.
  Install scripts используют DO/PLpgSQL без явного requires в control; после DROP
  первый pg_cron DO падает 42704. Сохранить builtin после точной сверки version,
  schema и owner, учитывать его в dependency order и проверить итоговую копию.
- `pg_restore --list` показывает выбранные TOC entries: DATABASE и DATABASE
  PROPERTIES скрыты без `--create`. Не объявлять их отсутствующими в архиве по
  отфильтрованному списку. В custom-формате DATABASE архивируется независимо от -C.
- DATABASE/PROPERTIES при --create обрабатываются независимо от use-list:
  поздний properties-only проход попытается создать БД повторно. Восстанавливать
  definition, settings, ACL/comment/security label одним начальным native pass,
  затем импортировать остальные объекты без --create. Проверять этот порядок
  на настоящем PostgreSQL с заполненными DB/role settings и ACL до серверного запуска.
- При холодном восстановлении сохранить исходное имя bootstrap-роли OID 10.
  В PostgreSQL 17 явный `GRANTED BY` для обычной роли без ADMIN option может
  завершаться 42501 даже при SUPERUSER. Не исправлять это переписыванием grantor
  или добавлением прав: воспроизвести исходную начальную роль и все memberships.
- `pg_restore --list` и выборочные TOC-проходы могут завершиться до конца stdin.
  Обычный Node pipe после этого оставляет producer без читателя; игнорирование
  EPIPE не предотвращает зависание. Полностью расшифровать архив в закрытый
  tmpfs изолированного контейнера, проверить все producer exit codes, затем
  использовать один seekable-файл для всех проходов. Не считать consumer exit 0
  доказательством успешной расшифровки и не сохранять plaintext на диск хоста.
- В диагностике указывать фактический этап: сообщение об успешном восстановлении
  preloads не позволяет приписывать ему последующий отказ чтения оглавления.

## 13.11.2026 — NULL и пустой ACL при сверке восстановления

- `NULL` в объектном ACL означает default privileges, а `{}` — явное отсутствие
  grants. Подстановка `acldefault` для обоих состояний скрывала реальное различие
  доступа; у функций defaults включают `PUBLIC EXECUTE`. Нормализовать только
  порядок ACL и доказанно эквивалентные права владельца, defaults — лишь для NULL.
- Проверять не только равенство снимков, но и `has_function_privilege` /
  `has_table_privilege` обычных ролей; тестировать различие в обоих направлениях.
  Успех старой сверки не доказывает ошибку данных, но затронутую проверку нужно
  обоснованно повторить исправленным инструментом без повторного импорта.

## 12.11.2026 — read-only через Session pooler

- `PGOPTIONS` не является доказательством режима конкретной транзакции через
  pooler. Проверка `default_transaction_read_only` ошибочно отклонила уже
  аутентифицированное подключение. Запрос метаданных выполнять внутри явной
  `BEGIN ... READ ONLY`, проверять `transaction_read_only`, завершать `ROLLBACK`.
  Default `off` допустим, actual `off` — отказ. Тестировать оба сочетания.
- Общая ошибка после JSON не доказывает неверный пароль. Указывать только
  безопасную диагностику версии и read-only без credential-данных; при валидных
  сохранённых файлах не просить повторный ввод и не сбрасывать пароль.

## 12.11.2026 — точность SSH и завершение локального этапа

- Визуальная расшифровка SHA-256 из мелкого VNC-скриншота перепутала регистр,
  slash и похожие символы. По отчёту локального Codex сетевой ключ совпал с VNC,
  а опубликованная строка — нет. Не принимать ключ по ошибочной строке и не
  отключать проверку. Сохранять текстовый публичный ключ, вычислять fingerprint
  штатной утилитой и сверять с независимым доверенным источником.
- `Permission denied` в BatchMode доказывает отказ автоматического входа,
  а не ошибку существующего пароля: пароль в этом режиме не проверяется.
- Сообщение владельца «готово» не заменяет отчёт исполнителя. Статус
  «заблокирован» означает, что SSH/канал/TLS/SQL ещё требуется завершить;
  не начинать копирование и не объявлять подключение готовым.

## 12.11.2026 — сетевой доступ для полной копии

- HTTPS-загрузка файлов на VPS и рабочий Docker не доказывают доступ к исходному
  PostgreSQL. Проверять исходящий TCP на точный Session pooler:5432 до запроса
  секрета. В данном запуске таймаут наступил на `socket.connect`, до TLS/пароля.
- До выбора и оплаты площадки читать политику ограничений портов: у AdminVPS
  статья №561 включает TCP 5432. Запрашивать проверку и узкое исходящее исключение,
  сохраняя закрытыми входящие порты БД. Не заменять Session pooler транзакционным
  ради обхода ошибки, не отключать TLS и не открывать внешнюю целевую БД.
- Полная Python trace выводит слишком много стандартной библиотеки в VNC.
  Использовать короткие отметки этапов и ограниченные таймауты; подробную
  диагностику после установленной причины не повторять.

## 12.11.2026 — точность ввода в консоль VPS

- Вставка `https://` также исказилась в `https;`, после чего shell разделил
  команду. В проверенном обходе используется `curl --proto-default https` и URL
  без схемы; SHA-256 сверяется до исполнения скачанного файла. Прямой
  `pressSequentially` на canvas не поддерживается; не повторять этот способ.
- Состояние фонового VNC-экрана не считать доказательством зависания задания.
  Проверять активную консоль и безопасные метаданные, без текстов SQL/строк данных.
- В HTML VNC проверенная вставка `echo 1122aabb` дала `12ab`; повторные физические
  клавиши внутри пакета терялись. Разделение только соседних повторов недостаточно:
  `systemctl` превратился в `systemcl`. Пакеты без повторных клавиш помогли для
  простого текста, но `&&` стало `77`, `_` стало `-`. Проверять команду целиком до
  Enter; запуск задания не равен успешному выполнению. Первый unit вернул код 100.
- Сложный установочный сценарий передавать файлом по HTTPS и сверять известный
  SHA-256 до исполнения. Не вставлять через такую консоль пароли и shell-синтаксис
  с неподтверждённой передачей. Для чтения нижней строки нужна полная страница:
  canvas 1024×768 частично выходил за высоту viewport и скрывал приглашение.
- Успешный `apt-get upgrade` не доказал обновление ядра: в `/boot` оставалась
  только версия `6.8.0-36-generic`. После отдельной установки `linux-generic`
  появилась `6.8.0-149-generic`; проверить журнал установки, затем перезагрузить
  пустой целевой VPS и подтвердить `uname -r` после нового входа. Исчезнувший
  transient unit проверять через `journalctl`, а не считать ошибкой установки.

## 11.11.2026 — сохранность административного доступа

- Временная среда исполнителя может очиститься между сессиями. Наличие публичного
  SSH-ключа в панели не доказывает возможность подключения: перед назначением
  проверить доступность закрытой части. Недоступный ключ не устанавливать.
- Постоянный ключ и аварийный доступ владельца сохранять в защищённом месте вне
  временной среды. В git, чат и пользовательские отчёты секреты не помещать.
  Порядок отзыва временных ключей входит в завершение миграции.

## 10.11.2026 — установка и постоянный адрес

- Событие установки приходит до открытия подсказки: перехватывать его при старте,
  вызывать только из нажатия. Согласие браузера не доказывает установку.
- Проверять доступность действий длинной инструкции на невысоком десктопе тоже,
  включая пояснение о временном адресе. Одних горизонтальных границ недостаточно:
  финальный рабочий экран может содержать больше текста, чем локальная страница.
- Отсутствие системной кнопки не означает ошибку пользователя. Оставлять ручную
  инструкцию и возможность работать без установки, в том числе внутри мессенджера.
- Переезд на другой домен не переносит PWA и очередь автоматически. Массовая
  установка начинается после выбора постоянного адреса и отправки старых записей.

## 09.11.2026 — повторный таймаут входа

- Успех с одной сети и ACTIVE_HEALTHY не доказывают вход директора/Android.
  Фиксировать таймаут как наблюдение, не утверждать недоказанную блокировку.
- Проверять отдельно Auth и БД. Диагностика доступна без входа, со временем и
  сборкой, без пароля/токена/заявок. У старой отменённой проверки нет права менять UI.
- Контроль доступности требует внешнего расписания, проверки его запуска и
  отдельного наблюдения с целевой сети. Документ не заменяет дежурного/оповещение.
- «Отказ» не корзина. Удаление явно подтверждается и восстанавливается, старая
  вкладка не меняет удалённую заявку, чужая роль не видит корзину.

Это журнал практических уроков, а не список новых функций. Обязательные правила

Отдельные предметные ограничения: плёнки поставляются листами; число заготовок
на листе зависит от вида плёнки. Не приравнивать один лист к одному телефону и
не выводить достоверную розничную выручку из количества купленных листов.

- Старая PWA на телефоне: кешированный HTML и ожидающий worker удерживали старый вход. Навигация теперь предпочитает сеть; версия проверяется на возврате, перезагрузка защищает ввод и очередь. Проверять не только новый профиль браузера.
- При повторном импорте нельзя запускать старый первичный импорт с удалением выручки/смен. Сравнивать каждый день, проверять месячные суммы и повторяемость дополнения.
- Мобильная колонка `1fr` сохраняет автоматический минимум; вложенная карточка и длинное имя файла могут растянуть всю страницу. Проверять вложенные grid/flex-блоки и фактическую ширину документа, а не только верхний контейнер.
- Поля наследовали 14,5 px, а компактные селекторы CRM — 11–12 px. На iPhone фокус маленького поля может увеличивать visual viewport, после чего всю страницу можно панорамировать. На сенсорных экранах шрифт полей не меньше 16 px; ручной pinch zoom сохраняется. Отдельно проверять обычный фокус/закрытие клавиатуры, `visualViewport.scale`, ширину документа и прокрутку таблиц/канбана; отключение корневого overscroll устраняет движение на границе, но не заменяет проверку переполнения.
- Кнопки в одной flex-строке с заголовком способны оставить тексту ширину одного слова. На телефоне выделять действиям отдельную строку и проверять длинные заголовки.
- Общий `overflow-wrap: anywhere` у кнопок позволял действиям роялти сжаться до одной буквы на строке даже на компьютере. Пустая QA-таблица и проверка только ширины документа этого не обнаружили. Кнопки не сжимаются; действия таблицы имеют естественную ширину и неразрывные подписи. В QA обязательны заполненные общая и помесячная таблицы, несколько валют, desktop-ширины и проверка геометрии кнопок.
- Корпоративный документ может содержать устаревшие условия и фрагменты чужого шаблона. Наличие ссылки не оправдывает перенос таких цифр в действующий регламент; неизвестное остаётся пустым.
- Смена домена не обновляет уже открытую анкету. Для поздних заявок нужен проверенный перенос исходных UUID; повторный вызов `lead_submit` меняет UUID и повторяет дедупликацию. Данные карточек, уже исправленные менеджером на цели, не перезаписываются.
- Зафиксированный upstream не гарантирует актуальные настройки и исправления безопасности каждого образа. Перед переносом проверять changelog, patch-версию PostgreSQL и значение Auth URL; в новом стеке `API_EXTERNAL_URL` включает `/auth/v1`, клиентский URL — без суффикса.
- «Доступно» с учётом ожиданий и остаток всей сети не доказывают возможность отгрузки с основного склада. Для закупок читать выбранный склад, вычитать его резерв и учитывать резерв без склада отдельно; неизвестные значения и пересчёт не превращать в ноль. Проверять неполные страницы и устаревший снимок.
- Отсутствующий товар, открытый заказ поставщику и его статус не устанавливают обещанный срок. Подтверждение поставки хранится отдельно со ссылкой на документ, количеством, датой и автором; после приёмки его нужно уменьшить. Несколько партий нельзя суммировать с датой самой ранней партии.
- Базовая единица, упаковка и число вырезов на листе различаются. Сохранять единицу конкретного UUID; исключения не исправлять массовой заменой. Название и артикул не ключи интеграции, поскольку могут повторяться.
- API МойСклад позволяет резервировать отсутствующий товар. Проверка остатка и запись резерва не гарантируют атомарную продажу последней единицы при других каналах. До проверки общего порядка резервирования отправка корзины называется заявкой; ручное подтверждение документа не выдаётся за автоматическую сверку API.
- Новые приватные таблицы закупок могли выпасть из прежнего жёстко заданного списка резервирования. Копия включает каталог, заявки, события, подтверждения поступлений и ключи повторов; восстановление проверяет пользовательские ссылки, номера и повтор операции после восстановления.
- Датированные бизнес-данные при сверке копий сравниваются в одном часовом поясе. Разный текстовый UTC offset не является изменением события; точное сравнение выполняется после согласования timezone, без округления временных значений.
- Каталог может выглядеть полным при пустых разделах. Проверять опубликованное
  содержание по рабочим сценариям, показывать недостающий ответ и путь обращения.
- Тесты поиска на коротких синтетических текстах не подтверждают релевантность
  реального корпуса. Прогонять рабочие запросы на закрытой восстановленной копии;
  сохранять исходный запрос в журнале, даже если поиск нормализует ё/е.
- Серверная очередь требует проверки стыка SQL и HTTP: версия конфигурации должна
  передаваться исполнителем, а успешный `void` RPC может вернуть пустой ответ.
  Изолированные тесты двух сторон не обнаруживают несовпадение их контрактов.
- Один товар может занимать две строки согласованного заказа: 8 сейчас и 12 позже
  с разными ценами. Сверять набор коммерческих строк, сохраняя количество и цену,
  а не запрещать повтор UUID товара внутри внешнего документа.
- Неопределённый ответ после POST и подтверждённый отказ — разные состояния.
  Сверка не должна создавать документ заново или требовать текущей цены уже
  созданного заказа. Отзыв сессии после потери ответа не разрешает клиенту менять
  исходный ключ повтора.
- Сумма корзины должна соответствовать создаваемому документу. Если интерфейс не
  рассчитывает дополнительный НДС, автоматизация допускает только включённый в
  цену НДС либо его отсутствие; неподдержанные скидки и валютные правила блокируются.
- Новые типы колонок приватной схемы тоже требуют пробного восстановления.
  `uuid[]` нельзя восстанавливать как JSON-строку; проверять заполненные настройки,
  неизменяемый состав заказа, `syncId` и повтор отправки после restore.

## 2026-11-09 — простота и контроль суммы дня

- Итог владельца и смены нельзя складывать как независимые продажи. Итог включает
  смены; способ оплаты неизвестной части не выдумывается (ADR-0016).
- Сравнение 31-дневного месяца с февралём ограничивать концом февраля.
  Нулевой профиль дня недели не должен приводить к делению на ноль в прогнозе.
- Сотрудник после удаления остаётся в расчёте зарплаты за отработанные смены.
  Даже открытая смена сохраняется, а серверная сессия отзывается.
- Скрыть процент заполняемости только CSS недостаточно: убрать из ответа рейтинга.
- Две вкладки разных аккаунтов требуют отдельных ключей сессии и кеша.
- Вопрос из статьи начинается с пустого поля; контекст показывается отдельно.

## 2026-11-09 — роли, клавиатура и условия смены

- Company scope не даёт права менеджера: техническую роль проверять отдельно и
  на клиенте, и в SQL/RLS. Редактор знаний не получает финансы партнёра.
- При расширении JSON ответа брать последнюю версию функции: ранний staff_home
  содержит сводку точки, которую последующая миграция уже убрала для продавца.
- Новые FK приватных таблиц включать в backup/restore. Проверять копию предыдущей
  схемы: отсутствие нового поля — не NULL и не разрешение сменить старую оплату.
- visualViewport.offsetTop нельзя переносить на весь корень: это повторяет
  автоматическую прокрутку Safari. Диалог прокручивает только собственное тело,
  шапка/действия остаются доступны; фокус открытия не перемещает фон.
- innerHeight и visualViewport могут уменьшиться одновременно. Клавиатуру
  определять относительно высоты до фокуса, а не только разностью этих двух чисел.
- Условия оплаты фиксируются в смене при открытии. Дефолт новой формы не должен
  менять контракт старого staff_create или уже начисленную зарплату.

## 09.11.2026 — непрерывное обучение

- Ежедневное напоминание не означает лимит один урок в день. Раздел, посещение,
  чтение, попытка и зачёт должны быть раздельными событиями.
- Не выводить имя владельца вместо имени вошедшего сотрудника: scope_name описывает
  область доступа, а full_name — человека.
- Банки вопросов подбираются по содержанию, а не по одинаковому числу на статью.
  Непроверенные видео и старые формы сначала требуют проверки, затем публикации.
- Новые обязательные колонки затрагивают восстановление и в private-схеме:
  вставлять только поля, существовавшие в исходной копии, сохраняя DEFAULT.
- Не менять ожидаемые результаты финансовых проверок ради реализации. Сначала
  проверить реальные поля возврата composite RPC и фактическую сохранённую смену.

## 09.11.2026 — простота запуска и ошибки смен

- Личный курс сотрудника и управление обучением — разные задачи. Владельцу не
  назначать курс автоматически; рабочие вопросы не подменять стратегией компании.
- Не использовать неизменяемое closed_at как версию редактирования суммы. Нужен
  отдельный счётчик, общий для правок сотрудника и руководителя.
- Пустое поле и введённый 0 — разные намерения. Неверный ввод не должен отправлять
  предыдущее корректное значение молча. Нулевой итог требует явного подтверждения.
- Ошибки отмены должны быть видимы и при открытой смене. Старая открытая смена не
  разрешает обход закрытого финансового периода; автоматически закрывать её нулём
  или выдуманным временем нельзя.

## 12.11.2026 — проверка фактической выгрузки и резервирования

- Успешное создание экспортированного snapshot не доказывает, что последующий
  heartbeat по тому же psql-процессу отвечает. До повторной полной выгрузки
  диагностировать `snapshot_heartbeat_timeout`; не ослаблять read-only/TLS и не
  объединять частичные артефакты из разных снимков.
- Кадр VNC может оставаться старым после фонового выполнения даже при клике
  в canvas. Сверять результат после безопасного обновления ввода/переподключения,
  не объявлять процесс зависшим или успешным по прежнему кадру.
- Сохранённые S3 lifecycle rules не равны работающему резервированию: отдельно
  проверяются загрузчик, расписание, запас ёмкости, чтение копии и восстановление.
- Ошибка IndexedDB не является пустой очередью. Проверка перед выходом и очистка
  черновиков согласуются одной транзакцией, очередь выходом не удаляется. Ошибка
  локального удаления после успешной команды должна оставить исходный UUID для
  безопасного повтора, а не показывать ложное «отправлено».
- Между getSession и фактическим fetch другая вкладка может сменить пользователя.
  Для отправки очереди токен проверенного владельца привязывается к конкретному
  запросу; общие headers клиента не меняются. Конфликты и неизвестные старые
  ошибки не становятся retryable от переключения navigator.onLine.

### 14.11: разрешение на данные, срок capability и понятный owner handoff

Владелец явно одобрил один live и два final Source→VPS snapshot; не просить
то же разрешение снова и не подменять им другие gates. У approved scope один
неизменяемый SHA и общий durable VPS budget: новая capability/новый пакет не
сбрасывают использованные/неопределённые попытки. Истёкший T36 secret не продлевать;
новый machine secret создавать только на VPS в свежем pinned task.

Предыдущий T30 handoff предполагал, что владелец понимает термин «независимый ключ»
и уже знает, где его копия. Это не было доказано. Давать цель проверки, официальный
кабинет/конкретный VPS, короткую команду и безопасные остановки при login Linux
или отсутствии копии. Не просить ключ в чат, не считать серверный identity
независимым хранением, не заставлять владельца искать ещё не переданный ему ключ.
Key proof — final gate, не причина тормозить уже разрешённый read-only live audit.

Один task включает prepare→hash-only READY→coordinator deployment/readback→один run.
Ожидание координаторского deploy прямо названо; после его подтверждения новый
пакет/повторное owner согласие не нужны. Passed restore/builds/RLS/Telegram не
переоткрывать; проверять реально изменённый транспорт и текущую свежесть копии.


### 14.11: actual технический preflight до одноразового вызова

T37 доказал прямой encrypted HTTPS Source→VPS полный snapshot:62tables/4020rows,
только1 source-newer Auth updated_at. Не возвращаться к TCP/MTU, не повторять
живую Auth-сверку до freeze. Ledger used1/3; secret rotation не сбрасывает used.
Reader после результата закрыт v2/GET410; availablelogs дают только наблюдаемое
окно, не гарантию всего хранения провайдера.

Перед T40 реальный SELECT DISTINCT backend_type (без Auth/businessrows) обнаружил
`pg_net 0.20.4 worker`; конечный enum и затем слишком узкий regex отклонили бы
валидное состояние. Исправление сделано до VPS one-shot; этот observed label
покрыт regression. Фиксированный metadata allowlist не расширялся, поле остаётся
техническим, fence-предикаты не ослаблены. Не путать локальные тесты с фактической
совместимостью Supabase extensions.

Log-query API принимает простой SELECT; WITH-expression/CTE не прошли parser/
переписывание запроса. Для будущих cleanup использовать проверенный plain SELECT
с inline aggregate expressions, explicittimewindow и только counts; raw logs
не возвращать.
