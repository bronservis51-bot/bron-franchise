# Правила работы над «Бронь Сервис — Франшиза»

Эти правила относятся ко всему репозиторию и к любому ИИ-разработчику. Здесь уже
рабочая система с настоящими данными. Указания о демонстрационном стенде в старых
ADR описывают историю и не разрешают менять рабочую базу как демо.

## Перед изменением

- Прочитай [описание продукта](docs/product-and-operations.md), относящиеся к задаче
  [уроки](docs/lessons-learned.md), ADR и runbook. Проверь фактический код и состояние
  целевого окружения. Название переменной или успешный локальный тест не доказывают
  состояние опубликованного приложения.
- Определи, какие роли, данные и внешние процессы затрагиваются. Делай минимальное
  законченное изменение. Не переписывай архитектуру и не добавляй зависимости ради
  удобства генерации кода. Сохраняй существующее оформление и русские названия.
- Не повторяй вопросы, уже решённые владельцем. Продолжай обратимую работу в рамках
  задачи; отдельно сообщай только о реальных внешних препятствиях и расходах.

## Неприкосновенные условия

1. **Заявки с лендинга продолжают поступать.** Отдельный репозиторий
   `bronservice-franchise` вызывает `POST /rest/v1/rpc/lead_submit` с
   `{ "p_lead": { ... } }`, успех — `{ "ok": true }`. Право `anon` на отправку
   необходимо; чтение заявок анонимам запрещено. Закрытие регистрации или смена
   входа не должны ломать этот контракт. При переносе учитывай старые открытые
   формы и новые заявки за время копирования. Не засоряй рабочую очередь тестами.
2. **Настоящие данные сохраняются.** Не запускай seed, reset, wipe и демо-аккаунты
   на рабочей базе. Перед миграцией — закрытая копия, пробное восстановление,
   сверка UUID, прав, сумм по валютам и файлов. Не изменяй уже применённые SQL:
   `schema_migration` проверяет их контрольные суммы. Изменение — новой миграцией.
3. **Каждая роль проверяется сервером.** Используй существующий адаптер
   `src/platform/backend.ts`, RLS и именованные RPC. Скрытая кнопка не является
   защитой. Проверяй доступ к конкретному партнёру/точке; `authenticated` недостаточно.
   Роли нельзя брать из пользовательского `user_metadata`. У привилегированных
   функций нужны явные grants, фиксированный `search_path` и проверка полномочий.
   Не добавляй `SECURITY DEFINER` для устранения ошибки доступа; существующие такие
   команды проверяй по [ADR-0004](docs/adr/0004-database-as-command-boundary.md).
4. **Отозванная сессия теряет доступ.** Сохраняй проверку `session_id` по
   `auth.sessions`, активности пользователя и назначений в RPC/RLS. Одного JWT
   недостаточно. Не возвращай общий пароль, публичный выбор ролей и авторегистрацию.
5. **Секреты и персональные данные не публикуются.** В клиенте допустимы URL и
   publishable/legacy anon key. Запрещены `service_role`, secret key, пароль БД,
   токен МойСклад, выгрузки, пароли пользователей и внутренние документы в git,
   сборке, логах и скриншотах. Закупочную себестоимость УК и личные расходы/зарплаты
   нельзя раскрывать другим партнёрам. Публичность рейтинга — отдельный контракт.
6. **Финансовые записи не теряются и не дублируются.** Сохраняй ключи повторов и
   контроль версии выручки/смен. Старую очередь без версии не применяй вслепую.
   Ошибка IndexedDB не означает «сохранено». Ожидающие записи нельзя терять при
   выходе, обновлении PWA или смене пользователя. Показывай ошибки и конфликты.
7. **Суммы имеют смысл и источник.** Деньги — целые минимальные единицы,
   проценты — basis points. Не складывай RUB/TRY/KZT без явного курса. Розница,
   роялти и поставки УК — разные потоки. Заказ, оплата и отгрузка — разные события;
   возвраты вычитаются. Нет данных/ошибка загрузки — не нулевая продажа. Остаток
   после введённых расходов не называй подтверждённой чистой прибылью.
8. **Интеграции независимы.** МойСклад читается только серверным токеном с
   минимальными правами; сбой не блокирует смены и выручку. Полная выгрузка заменяет
   снимок атомарно, с датой успешного обновления. Контрагентов не объединяй по
   одному имени. Покупки материалов не доказывают розничную выручку партнёра.

## Проверка и завершение

- Для кода: `npm run typecheck`, подходящие тесты и `npm run build`; после изменения
  SQL-контрактов — `npm run gen:contract` и проверка diff. При изменении доступа
  проверь разрешённые действия, чужую область, анонима и отозванную сессию; при
  финансовой записи — повтор, конфликт и сетевой сбой. Не добавляй формальные тесты
  для документации: проверь ссылки и `git diff --check`.
- Учитывай часовой пояс точки и границу месяца. Тестовые часы JavaScript и SQL
  должны совпадать; настройку тестов `Europe/Moscow` не заменяй случайным временем CI.
- Различай «код написан», «SQL применён», «CI прошёл», «версия опубликована» и
  «проверена в рабочем окружении». При отсутствии подтверждения так и сообщай.
  Истёкшее подтверждение операции не означает успех; сначала проверь результат.
- Обновление архитектуры фиксируй новым ADR, ошибку — в журнале уроков, порядок
  эксплуатации — в runbook. Старое решение помечай заменённым, а не стирай историю.
  Текущий переход: [ADR-0010](docs/adr/0010-operational-release-and-russia.md).
- В завершении сообщи результат, проверки, ограничения и следующий конкретный шаг.
  Не обещай абсолютной безопасности, юридического соответствия от одного переезда
  или «миграции одним промптом» без инфраструктуры и пробного восстановления.
