# Перенос в Timeweb

Это подготовка, а не отметка о завершённом переезде. Не запускать на источнике.
Домен приложения — `app.bronservis.ru`, лендинг — `bronservis.ru`, API —
`api.bronservis.ru`. Регистрируется только `bronservis.ru`; `app` и `api` —
бесплатные поддомены. Решение владельца и последствия:
[ADR-0022](../../docs/adr/0022-bronservis-domain-and-subdomains.md).
Оба сайта и backend размещаются в РФ. Домен и сервер —
разные услуги; парковка домена не предоставляет Docker/PostgreSQL.

## Целевая площадка

Один российский VPS: минимум 2 CPU / 4 GB / 50 GB SSD; для полного стека
предпочтительно 4 CPU / 8 GB / 80 GB. Перед оплатой сверить текущую цену,
публичный IPv4, стоимость резервирования и условия продления доменов. Отдельный
сервер для каждого сайта и платная GitHub-подписка для этого переноса не нужны.
Один VPS остаётся единой точкой отказа; независимые копии обязательны.

ОС — поддерживаемая Ubuntu LTS с Docker Engine/Compose из официального источника.
Compose не ниже 2.24.4: override использует `!override`, чтобы заменить, а не
добавить публичные порты. Конфигурация проверена Compose 5.7.0 и Caddy 2.11.8;
контейнеры и восстановление на новом сервере ещё не запускались.
Не устанавливать WordPress, коммерческую панель или приложение через случайный
one-click образ. Не открывать PostgreSQL, pooler и Studio наружу. Во внешнем
firewall разрешены HTTP/HTTPS и ограниченный административный SSH; отдельно
проверить, что Docker не обошёл ограничения firewall.

## Фиксация стека и подготовка

Проверенный исходник конфигурации Supabase: репозиторий `supabase/supabase`,
commit `5583c2bd6f7e0ba368dcaeb0db20ce190b94317d` от 04.11.2026. Он содержит
PostgreSQL 17 и gateway **Envoy**, сервис `api-gw`. Не применять старые override
для сервиса `kong`. Не подменять образы на `latest`. Перед фактическим развёртыванием
проверить advisories, доступность образов и совместимость Auth/Storage с источником.
Отдельно проверить patch-версию PostgreSQL: исходная база уже на 17.11, а образ
в зафиксированном upstream может отставать. Такой образ не допущен в production
без обновления до поддерживаемого исправленного релиза и репетиции восстановления.

1. Получить именно этот commit, скопировать каталог `deploy/timeweb` в `docker/bron`.
2. По официальной инструкции создать закрытый `docker/.env` с новыми секретами.
   Заполнить все поля upstream; не оставлять примеры паролей. Никаких секретов в git.
   `SITE_URL=https://app.bronservis.ru`,
   `SUPABASE_PUBLIC_URL=https://api.bronservis.ru`,
   `API_EXTERNAL_URL=https://api.bronservis.ru/auth/v1`. В текущем upstream
   Auth URL включает `/auth/v1`; URL клиентского SDK остаётся без этого суффикса.
   Регистрация закрыта; доступы создаёт менеджер.
   Публичный клиентский ключ и JWT должны соответствовать новой установке.
   Auth redirect URLs перечисляются явно; не вводить общие авторизационные cookies
   на родительском домене. Существующая сессия клиента хранится в browser storage
   конкретного origin. Для DNS нужны записи `@`, `app` и `api` на проверенный IP
   российской цели; не публиковать непроверенный IPv6 или wildcard-запись.
3. Проверить объединённый `docker compose ... config`, образы через `pull`,
   затем поднять изолированную цель. Не применять seed и `reset.sh`.
4. Восстановить roles/schema/data по официальной процедуре. Не восстанавливать
   поверх уже работающей цели. Проверить расширения и версии Auth/Storage; полный
   перенос включает Auth UUID, хеши паролей, identities и прикладные схемы.
   Данные Storage копируются отдельно от SQL, с контрольными суммами.
   До открытия API аннулировать восстановленные сессии и refresh tokens **на цели**,
   сохраняя `auth.users` и `auth.identities`. Нового JWT secret недостаточно для
   отзыва перенесённых refresh tokens. Проверить отказ обмена старого токена;
   на исходном проекте этот шаг не выполнять.
5. Выполнить `npm run migration:check` с двумя закрытыми connection strings.
   Он сравнивает все таблицы `public`/`app_private`, `auth.users`/`auth.identities`,
   определения RPC, RLS, grants объектов, индексы, ограничения и последовательности.
   Это строгая сверка до пробных входов: вход меняет Auth-метаданные. Любое
   расхождение разбирается явно. БД доступна для сверки только через SSH-туннель.
6. Отдельно проверить Auth/RPC, роли, чужую область, отозванную сессию, anon submit
   без права чтения, денежные итоги по каждой валюте, документы, резервирование
   и пробное восстановление. Равенство хешей не заменяет эти проверки.

## Сборки сайтов

Приложение собирается с `VITE_BASE_PATH=/`, новым `VITE_SUPABASE_URL`,
соответствующим публичным ключом и `VITE_APP_ENV=production`. Его `dist/`
попадает в `docker/bron/site/app/` целиком, включая worker, manifest и версию.
Второй backend или пользовательские пароли в frontend не добавляются.

Лендинг берётся из отдельного `bronservis51-bot/bronservice-franchise`, а не из
экспериментального проекта. На дату подготовки рабочая версия — commit
`fb5210c` (перед сборкой проверить актуальный HEAD). Копируются публичные файлы
сайта без `.git`, внутренних инструкций и секретов в `docker/bron/site/landing/`.
Перед размещением обновляются только API URL/публичный ключ и абсолютные
метаданные домена; анкета сохраняет `POST /rest/v1/rpc/lead_submit`,
`{"p_lead":{...}}` и ответ `{"ok":true}`. Функциональность не переписывается.

`Caddyfile` обслуживает HTTPS и сжатие; HTML/worker/version не кешируются надолго,
хешированные assets кешируются на год. API опубликован только по путям Auth,
REST и Storage. Содержимое Studio извне недоступно.

## Переключение и старые адреса

Сначала полная репетиция, затем короткое окно переключения. Источник сохраняется
до сверки. После запуска целевая БД — единственное место записи денег. Простая
смена DNS не переносит данные, активные сессии или очередь PWA.

- Перед финальной копией завершить отправку очередей на старом адресе.
  Не очищать IndexedDB, кеши, локальные записи или пользовательские сессии вслепую.
- Старый кабинет GitHub Pages обновить на новый backend и пока оставить доступным:
  записи очереди остаются в старом origin и смогут отправиться после повторного
  входа тем же UUID. Переносить пароли и UUID, но не действующие старые сессии.
- Не ставить безусловный redirect перед обработкой очереди. Новая установка PWA
  создаётся с нового адреса; прежняя иконка не меняет origin автоматически.
- Открытые старые анкеты продолжают обращаться к прежнему API. До переключения
  должен работать проверенный перенос поздних лидов по исходным UUID без
  перезаписи работы менеджера. Подготовлен `npm run migration:leads`: сначала
  проверка без записи, запись только с `-- --apply`.
  [Порядок и ограничения](../../docs/runbooks/late-leads.md).
  **Мост проверен локально, но ещё не развёрнут; до его запуска и проверки
  на новой площадке финальное переключение запрещено.**
- Проверить оба лендинга, анкету и правильное распределение заявки. В production
  не создавать фиктивные финансовые записи и лиды; запись проверять с SQL-откатом,
  HTTP — отклоняемым без записи payload, поступление реальных лидов — по UUID.
- После новых записей на цели откат требует обратной сверки. Возврат DNS на старую
  независимую базу потеряет эти записи. До начала окна зафиксировать журнал изменений
  и способ их обратного переноса.

## Допуск к публикации

Проверить desktop 1280/1366/1440/1920 и телефоны 320/360/390/430, светлую/тёмную
темы, текст 200%, реальные заполненные таблицы и все роли. Для роялти — отдельно
внутреннюю прокрутку, подписи действий, диалоги и Excel. Проверить установленную
старую PWA, её обновление, новую PWA, потерю связи и ожидающую запись. Не объявлять
переезд завершённым по наличию контейнеров, сертификата или успешного CI.

Проверить копии вне этого VPS и измерить восстановление. Настроить наблюдение за
HTTP/Auth/API, диском, памятью, ошибками копирования и последним успешным бэкапом.
Автоматическое резервирование не считается настроенным по одному этому файлу.
